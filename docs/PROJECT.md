# 产品定位与目标设计

> **注意**：面板 v3（体检单版式）在分支 `v3/design` 上实现，尚未合并到 `main`。面板与菜单栏图标的设计真源是 [DESIGN_V3.md](DESIGN_V3.md)。数据、规则与提示词正文见 [DESIGN_V2.md](DESIGN_V2.md)。面板里的比熊已删除（用户原话 U10）。[DESIGN.md](DESIGN.md) 中被取代的章节已有标记，其余章节仍有效。本文件与 DESIGN_V3.md 冲突时，以 DESIGN_V3.md 为准。

MoleMonitor 是 macOS 菜单栏上的轻量状态监测与预警工具。它只检测和预警，不做清理。清理由用户的 agent 调用 Mole CLI 完成。本文件描述产品范围、健康规则和数据口径。四个阶段和面板 v2 的代码都已写完，见 [当前状态说明](#当前状态说明)。

## 1. 产品定位与需求摘要

本节把"用户需求"和"设计补充"分开标注。用户需求是用户提出的目标，编号 R1 至 R9。设计补充是设计者的判断，用户未明确要求，可以调整。

### 1.1 用户需求

| 编号 | 用户需求 |
|---|---|
| R1 | 做一个好看、方便、极其轻量的 macOS 状态监测小工具。它与 Mole CLI 配合使用，替代很重的同类清理软件。 |
| R2 | 本工具只监测与预警，不做清理。清理由用户的 agent 调用 Mole CLI 完成。目标是尽可能少常驻、减轻系统压力。 |
| R3 | 及时观测四类异常：近期磁盘占用突然大量增加（例如 5 天多占用 300 GB）、CPU 异常、内存异常、耗电异常。 |
| R4 | 菜单栏做成"红绿灯"式，分别显示内存、CPU、温度的健康状态。设计要有趣但简洁。小狗（比熊）的奔跑状态表示 CPU。 |
| R5 | 点开菜单栏图标后弹出状态卡。磁盘等次要信息放在状态卡里。 |
| R6 | 磁盘短期大量占用、内存泄漏等严重问题要弹系统通知。 |
| R7 | 电池循环次数没有用，不显示。 |
| R8 | 提供 CLI 读取状态。 |
| R9 | 要看网速和流量消耗信息，放在状态卡里。不做每应用耗电排行。 |

### 1.2 设计补充

以下内容是设计者的判断，不是用户需求：

- 各项健康等级的阈值、持续时间和退出条件。
- 通知的冷却时间、全局上限和去重键。
- CPU 忽略列表和 `config.json`。
- `active_alerts` 里的 `agent_hint`（可对 agent 说的话）。
- 采样频率、存储格式和保留期限。
- CLI 子命令、字段结构和退出码。
- 菜单栏图标的静态与奔跑姿态和黄 ▲、红 ■ 角标（v3 前是三个静态姿势和红色角标）。
- 四个阶段的划分。

### 1.3 边界

本工具只检测和预警。问题消失后，工具不发通知，界面和 CLI 也不显示"已恢复"。状态自然变回正常即可。

## 2. 范围与不做的事

### 2.1 范围内

| 健康项 | 位置 | 说明 |
|---|---|---|
| CPU | 菜单栏（小狗） | 全机 CPU 与单应用占满 |
| 内存 | 菜单栏（方块点） | 内存压力、swap 增长、泄漏嫌疑 |
| 温度 | 菜单栏（水滴点） | 以系统热状态为主信号 |
| 磁盘 | 状态卡，红色时加菜单栏角标 | 短期增长量与剩余空间 |
| 耗电 | 状态卡，红色时加菜单栏角标 | 睡眠掉电，加整机耗电异常（设计补充，见 [DESIGN.md 6.8](DESIGN.md#68-健康等级与已持续)）。耗电是第 5 个健康项 |
| 网速与流量 | 状态卡 | 只在状态卡里，不进菜单栏 |
| 前 5 名应用 | 状态卡 | CPU 与内存两种排序 |

### 2.2 不做的事

| 不做 | 原因 |
|---|---|
| 清理、自动删除、sudo、特权 helper、SMC 写入、风扇控制 | 满足需求 R2。工具保持只读。 |
| 电池循环次数 | 满足需求 R7。 |
| 每应用耗电排行，以及用 CPU 使用率估算耗电 | 满足需求 R9。CPU 使用率不能替代能耗。 |
| 电池基线耗电 | 延后。两周使用后再决定。 |
| 恢复通知与恢复状态显示 | 见 [1.3 边界](#13-边界)。 |
| `events.ndjson` 与 `--events` | 第一版不做。 |
| 清理类提示词命令 | 复制给 Agent 的提示词禁止 `mo optimize`、`mo uninstall` 和非 dry-run 清理，见 [DESIGN.md 第 7 章](DESIGN.md#7-复制提示词规格)。状态卡的复制按钮已实现，v3 起文字是“复制排查提示词”。 |
| 每应用流量 | 第一版不做。 |
| 目录扫描 | 磁盘增长定位交给 agent 和 Mole CLI。 |
| Mole Go 采集器、`fetch_status.py`、`ps` 采样、1 Hz 界面定时器 | 采集范围超出需求，且常驻成本高。 |
| SMC 温度判定规则 | SMC 温度和风扇只显示数值，不参与判定。 |
| 网络端口与网络服务连接 | 工具不联网。 |

## 3. 健康模型

### 3.1 通用规则

每个健康项有一个健康等级。健康等级取下表中的一个值。

| 健康等级 | 含义 | 菜单栏表现 |
|---|---|---|
| 绿 | 正常 | 绿色单色，跟随菜单栏颜色 |
| 黄 | 需要留意，暂时不影响使用 | 黄色 |
| 红 | 已影响使用，或很快会影响 | 红色，红点外加圈 |
| 灰 | 未取得：设备没有该传感器，或读取失败 | 空心灰点 |
| 过期 | 最新样本比允许的时间旧 | 空心灰点加虚线边 |

规则如下：

1. 所有时长按样本时间戳计算，不按样本个数。
2. 等级判定由"进入条件加持续时间"组成。条件必须持续满足，等级才升高。
3. 退出阈值比进入阈值低一档。这叫迟滞，用来防止数值在阈值附近来回跳。
4. 升级可以直接跳级。降级每次只降一级。
5. 样本缺失时不升级也不降级。连续缺失超过过期时限后，该项变为"过期"。
6. 读取失败、设备没有、样本不足这三种值都不当作 0。

### 3.2 CPU

**结论**：CPU 看两个信号。一个是全机均值，另一个是单个应用长时间占满一个核。

**通俗解释**：打开网页或编译代码时，CPU 短时冲到 100% 是正常的，所以只看长时间均值。另一种常见问题是某个程序卡在循环里，一直占满一个核。在 10 核的 Mac 上，全机均值可能只有 10%，但这个程序会持续耗电和发热。所以工具单独检查每个应用。

| 等级 | 进入条件 | 退出条件 |
|---|---|---|
| 黄（全机） | 5 分钟均值 ≥ 70%，持续 5 分钟 | 5 分钟均值 < 55%，持续 2 分钟 |
| 黄（单应用） | 某个应用 30 分钟均值 ≥ 90%（单核口径） | 该应用 10 分钟均值 < 50% |
| 红（全机） | 10 分钟均值 ≥ 90%，持续 10 分钟 | 5 分钟均值 < 75%，持续 3 分钟 |

- 单应用占满一个核只到黄，不到红。原因是全机还有余量。
- 默认忽略列表包含系统后台进程：Spotlight 的 `mds_stores` 与 `mdworker`、`photoanalysisd`、`backupd`、XProtect 等。`config.json` 可以增删列表项。
- 睡眠期间不计入窗口。唤醒后窗口清空，前 5 分钟显示"样本不足"，等级保持唤醒前的值。
- 退出阈值（55% 与 75%）和单应用退出条件是设计补充，上线前用实测复核。

### 3.3 内存

**结论**：内存以内存压力等级和 swap 增长为主，不用已用百分比。

**通俗解释**：macOS 会把空闲内存用作缓存，所以"已用 90%"很常见，不说明有问题。系统自带"内存压力"判断，分正常、警告、严重三档。压力升高时，系统先压缩内存，再把内存写到磁盘上的 swap 文件。swap 在短时间内快速增长，说明内存真的不够。

| 等级 | 进入条件 | 退出条件 |
|---|---|---|
| 黄 | 内存压力为警告，持续 60 秒 | 内存压力为正常，持续 5 分钟 |
| 黄 | swap 30 分钟增长 ≥ max(2 GiB, 物理内存 12.5%) | swap 30 分钟增长 < 512 MiB |
| 黄 | 泄漏嫌疑应用 ≥ 1 个 | 嫌疑解除，规则见 [3.7](#37-内存泄漏检测) |
| 红 | 内存压力为严重，持续 30 秒 | 内存压力不高于警告，持续 5 分钟 |

状态卡里的"已用内存"只作参考，不参与判定。

### 3.4 温度

**结论**：温度以 `ProcessInfo.thermalState` 为主信号。SMC 温度和风扇转速只显示数值，不参与判定。

**通俗解释**：Apple 芯片在 90 °C 以上运行也可能正常。重要的是系统是否因为太热而降频。`thermalState` 是系统自己给出的"热到什么程度"的判断，分 nominal、fair、serious、critical 四档。它是公开接口，读取成本很低。

| 等级 | 进入条件 | 退出条件 |
|---|---|---|
| 黄 | `fair` 持续 10 分钟 | `nominal` 持续 3 分钟 |
| 红 | `serious` 持续 60 秒 | 不高于 `fair`，持续 3 分钟 |
| 红 | `critical`，立即 | 不高于 `fair`，持续 3 分钟 |

如果 Mac 上实测 `fair` 累计超过 20% 的时间，则把 `fair` 视为绿。此时黄色规则取消。这一项是验证项 V3。

### 3.5 磁盘

**结论**：磁盘看短期增长量和剩余空间，不看读写速率。

**通俗解释**：APFS 把一部分空间标为"可清除"，例如 Time Machine 本地快照和系统缓存。系统需要空间时会自动删除它们。如果把它们算作已用，快照的生成和删除会让已用量忽高忽低，造成误报。所以工具只统计"真实已用"。

| 量 | 定义 |
|---|---|
| 总容量 | `/System/Volumes/Data` 数据卷的总容量 |
| 重要用途可用容量 | `volumeAvailableCapacityForImportantUsage`，含可清除空间 |
| 真实已用 | 总容量 − 重要用途可用容量 |
| 增长量 | 当前真实已用 − 窗口内真实已用的最低值 |
| 净变化 | 当前真实已用 − 窗口起点的真实已用 |

增长量比净变化更准。例如 5 天前 200 GB，3 天前删到 150 GB，现在 450 GB。净变化是 +250 GB，增长量是 +300 GB。CLI 同时给出两个数。

| 等级 | 进入条件（满足任一条） |
|---|---|
| 黄 | 1 天增长量 ≥ max(20 GiB, 总容量 3%) |
| 黄 | 5 天增长量 ≥ max(60 GiB, 总容量 8%) |
| 黄 | 可用容量 < 总容量 15% |
| 红 | 1 天增长量 ≥ max(60 GiB, 总容量 8%) |
| 红 | 5 天增长量 ≥ max(150 GiB, 总容量 20%) |
| 红 | 可用容量 < 总容量 5%，或 < 15 GiB |

- 此处"可用容量"指重要用途可用容量。
- 磁盘规则的退出条件是设计补充：1 天和 5 天增长量都低于进入阈值的一半，且可用容量回到进入阈值加 3 个百分点。
- iCloud 优化储存卸载文件会使真实已用下降。下降不影响增长量判定，因为增长量取窗口最低值。
- 历史不足 N 天时，该窗口的状态是 `insufficient_window`。

### 3.6 睡眠掉电

睡眠掉电是耗电项的第一条规则。第二条规则是整机耗电异常，见 [DESIGN.md 6.8](DESIGN.md#68-健康等级与已持续)。

**通俗解释**：合盖睡眠时电量掉得很快，通常是某个程序阻止了睡眠。工具在睡前和醒后各读一次电量，算每小时掉电百分比。

| 等级 | 进入条件 |
|---|---|
| 黄 | 睡眠 ≥ 2 小时，掉电 ≥ 3%/小时 |
| 红 | 睡眠 ≥ 2 小时，掉电 ≥ 6%/小时 |

只在使用电池时判定。这是设计决定。接电源睡眠时，状态为 `not_applicable`。

### 3.7 内存泄漏检测

**原理**：泄漏的典型特征是一个应用的内存长时间几乎只涨不跌。正常应用的内存上下波动。

**数据来源**：

| 优先级 | 接口与字段 | 说明 |
|---|---|---|
| 1 | `proc_pid_rusage(RUSAGE_INFO_V6)` 的 `ri_phys_footprint` | 与活动监视器"内存"列接近 |
| 2（降级） | `proc_pidinfo(PROC_PIDTASKINFO)` 的 `pti_resident_size` | 结果标注 `basis: "rss"`，因为 RSS 会重复计入共享页 |
| 3 | 两者都读不到 | 该进程不参与判断，只计入覆盖率的"不可读"数量 |

进程用 `(pid, ri_proc_start_abstime)` 识别，避免 pid 复用。进程按 `.app` 包名归并为应用。

**四状态判定**（每个应用，每 5 分钟取一个点，时长按时间戳计算）：

| 状态 | 条件 |
|---|---|
| 候选 | footprint ≥ max(1 GiB, 物理内存 5%)，且应用最早进程已运行 ≥ 10 分钟 |
| 嫌疑 | 候选，且 60 分钟增长 ≥ max(512 MiB, 物理内存 3%)，且 12 个 5 分钟步长中 ≥ 10 个不下降，且最近 15 分钟仍在增长 |
| 确认 | 嫌疑持续 ≥ 120 分钟，且累计增长 ≥ 1 GiB。此时发通知 |
| 解除 | footprint 比最高点下降 ≥ 25%，或连续 30 分钟不增长，或应用退出 |

**诚实降级**：

- 状态卡和 CLI 显示"已检查 N 个应用，另有 M 个系统进程无权读取"。
- 如果内存压力不低于警告且 swap 持续增长，但可读应用都没有增长，则显示"系统内存持续增长，但没有找到可读的增长应用"。此时不发泄漏通知，只按 [3.3](#33-内存) 的规则处理。
- 只为 footprint ≥ 500 MiB 的应用保留历史，最多 20 个应用，每个 24 个点。

## 4. 菜单栏与状态卡

### 4.1 菜单栏

菜单栏图标是比熊侧视剪影，矢量绘制，画布 24 × 18 pt。图标只有两种姿态：静态和奔跑。图标规格见 [DESIGN_V3.md 4.2](DESIGN_V3.md#42-菜单栏图标静态与奔跑)。

| 状态 | 图标 |
|---|---|
| 正常 | 静态 1 帧，实心剪影，没有角标 |
| 留意 | 黄色 ▲ 角标，画在右下角 |
| 异常 | 红色 ■ 角标，画在右下角 |
| 采集中、过期 | 静态空心轮廓，不奔跑 |

- 奔跑：CPU 达到 35% 起，4 帧循环。35% 至 60% 为 4 fps，60% 至 85% 为 6 fps，85% 以上为 8 fps。
- 停止：CPU 低于 25%，且连续 2 个 30 秒 tick，回到静态。
- 退路：Reduce Motion、屏幕锁定、显示器睡眠、低电量模式时回到静态，计时器停止。
- 颜色不是唯一的区分方式。▲ 与 ■ 的形状也表示等级。
- 图标宽度目标 ≤ 40 pt，避免被刘海屏挡住。
- 每个图标有 VoiceOver 标签和 tooltip，例如"CPU 正常，内存偏紧，温度正常"。奔跑时标签末尾加“CPU 占用高”。

> **注意**：奔跑时才有一个图标计时器（不高于 8 Hz）。CPU 不忙时没有。1x 屏幕下剪影与角标的辨识度须在真机上检查。

### 4.2 状态卡

状态卡是一个自定义 `NSPanel` 窗口，版式是“体检单”。版面、尺寸和动效以 [DESIGN_V3.md](DESIGN_V3.md) 第 3 至 7 章为准。主列宽 352 pt。高度随问题行数变化：全绿 264 pt，1 个问题行 344 pt，2 个 392 pt，3 个 468 pt（最大）。点击或悬停一行时，右侧展开 320 pt 宽的侧栏。面板里没有比熊、气泡、舞台和位图素材。

问题优先：有问题的行排在前面，并带等级底色。主列从上到下有四段：

| 区域 | 内容 |
|---|---|
| 标题块 | 64 pt 高。一句话说结论，例如“磁盘 5 天胖了 314 GB，该让 Agent 看看了”。深色外观下，有问题时背后有状态光 |
| 分项区 | 问题行每行 72 pt，整行等级底色，行内有曲线，最多 3 行。正常项排成两列，每行 28 pt。网络没有等级，用中性圆点 |
| 记录行 | 28 pt。文字是“近 7 天 N 条记录 ›”，点击进入异常记录页 |
| 底部 | 32 pt。有问题时是主按钮“复制排查提示词”，无问题时是文字按钮“复制日常巡检提示词”，旁边有“···”菜单（CLI 命令、通知、退出）。提示词不超过 3000 字。复制成功后，按钮上落一个爪印章加“已复制”，1500 ms 后淡出 |

侧栏按分项显示：24 小时、7 天、30 天曲线（一图一线），一句统计，容量区，占用 App 或网卡排行。异常记录页顶部有 7 天时间带。

各区域的规则如下：

- 磁盘图数据来自 `DiskSeries`：每 6 小时取一个点，最多 120 个点。磁盘总结文字统一用十进制 GB（1 GB = 10^9 字节）。
- 趋势缓冲保存 2 小时，每 30 秒一个点。状态卡打开期间另有 2 秒细段。24 小时与 7 天曲线读 5 分钟汇总文件 `rollup-YYYY-MM.ndjson`。
- 整机 CPU 是所有核的忙碌 tick 占总 tick 的百分比（0 至 100）。
- 提醒区只列事件和时间。事件消失后，该行直接移除。

不放进状态卡的内容：电池循环次数、全部温度传感器列表、磁盘读写速率、进程命令参数、每应用耗电、每应用流量。

状态卡生命周期：

1. 状态卡打开时，创建视图并立即采样 1 次。
2. 状态卡打开期间，启动一个 2 秒的实时采样定时器（见 [6.1](#61-采样频率)）。
3. 状态卡关闭时，取消实时采样定时器，释放视图。
4. 状态卡关闭后，只剩引擎的 30 秒 tick，加奔跑时才有的菜单栏图标计时器（不高于 8 Hz）。状态卡关闭时没有高频采样定时器。

2 秒的实时点只放内存，不写入 `status.json` 和 NDJSON。30 秒趋势点每 5 分钟写入 `trend.json`。

## 5. 通知

### 5.1 通用规则

| 规则 | 值 |
|---|---|
| 接口 | `UNUserNotificationCenter` |
| 授权请求 | 每次启动时，如果授权状态是“未决定”，引擎立即请求授权，系统弹出授权框。同时首次启动自动展开状态卡，说明通知用途。不要等第一条异常时才请求。 |
| 去重键 | 事件类型加对象，例如 `memory_leak:<应用名>`、`disk_growth:<卷>` |
| 全局上限 | 每小时 3 条，每天 10 条。超出的事件只显示在状态卡提醒区。 |
| 唤醒后 | 唤醒后 5 分钟内不发 CPU 与温度通知 |
| 恢复 | 不发恢复通知 |
| 专注模式 | 由系统处理，工具不绕过 |

### 5.2 事件表

| 事件 | 触发条件 | 冷却与再通知 |
|---|---|---|
| 磁盘短期大量增长 | 磁盘等级因增长规则进入黄或红 | 自上次通知后，增长量再增加 ≥ 50% 才再次通知 |
| 磁盘剩余空间低 | 磁盘等级因可用容量规则进入红 | 24 小时 |
| 内存泄漏 | 泄漏检测进入"确认" | 同一应用 24 小时 |
| 内存严重不足 | 内存等级进入红 | 2 小时 |
| 全机 CPU 持续高负载 | 5 分钟均值 ≥ 85%，连续 30 分钟 | 每次持续高负载只发 1 条 |
| 单应用占满 CPU | 单应用占满一个核，连续 60 分钟 | 同一应用 24 小时 |
| 高温 | `serious` 持续 5 分钟，或 `critical` 立即 | 1 小时 |
| 睡眠掉电异常 | 睡眠掉电进入红 | 6 小时 |
| 整机耗电异常 | 整机耗电进入红 | 6 小时 |

- CPU 通知的初始值是设计补充，两周后按使用情况复核。
- 磁盘通知文案写"已排除可清除空间（快照、缓存）"。文案不写"不是快照"，因为工具不能证明增长来源。
- 泄漏通知文案用"可能"，例如"Chrome 内存 2 小时持续增长了 3.1 GB，它可能有内存泄漏"。
- 全机 CPU 红只在菜单栏和状态卡显示。通知用上表的持续高负载规则。

### 5.3 未授权时的降级

| 授权状态 | 行为 |
|---|---|
| 已授权 | 正常发送 |
| 未决定 | 状态卡里显示授权说明和授权入口。异常事件显示在提醒区。 |
| 已拒绝 | 不再请求。状态卡底部显示"通知已关闭，可在系统设置 > 通知中打开" |
| 请求失败（例如 ad-hoc 签名） | 同"已拒绝"，并在 CLI 字段 `notifications.authorization` 中写 `unavailable` |

## 6. 采样与存储

### 6.1 采样频率

所有定时器的容差是周期的 20%，让系统合并唤醒。睡眠时停止全部定时器。唤醒时重新开始，并清空短期窗口。

| 指标 | 状态卡关闭 | 状态卡打开 |
|---|---|---|
| 全机 CPU | 30 秒 | 30 秒 |
| 内存压力 | 系统事件加 30 秒复核 | 同左 |
| swap 与压缩内存 | 30 秒 | 30 秒 |
| 进程扫描 | 300 秒（全绿），180 秒（有黄或红） | 4 秒 |
| SMC 温度与风扇 | 热状态不是 `nominal` 时，每 60 秒 | 5 秒 |
| 电池 | 用电池时 60 秒，接电源时 5 分钟 | 同左 |
| 磁盘 | 15 分钟 | 15 分钟，打开时加读 1 次 |
| 网络计数器（写入记录） | 15 分钟 | 15 分钟 |
| 网速与整机 CPU（实时曲线） | 不采集 | 2 秒（已实现，仅显示） |
| `status.json` 与 `trend.json` 写入 | 5 分钟，等级变化时立即写 | 同左 |

- 实时采样（网速与整机 CPU）只在状态卡打开期间运行。状态卡关闭时，引擎取消 2 秒定时器并清空缓冲。实时点不落盘。
- 实时采样用单独的队列和单独的定时器，与引擎的 30 秒 tick 分开。
- 热状态为 `nominal` 且状态卡关闭时，不读 SMC。
- 热状态用系统通知事件，不轮询。
- 全绿且状态卡关闭时，进程扫描间隔 300 秒。有黄或红时 180 秒。泄漏检测的 5 分钟取点按时间戳对齐。

实现细节（采样计划见 [DESIGN.md 6.1](DESIGN.md#61-采样计划与唤醒预算)）：

- 引擎只有一个 30 秒 tick。每第 30 个 tick 采样一次磁盘，即每 15 分钟一次。每第 10 个 tick 写 `status.json` 与 `trend.json`，即每 5 分钟一次。
- 状态卡打开触发的采样有 30 秒去抖。距上次采样不足 30 秒时，不再采样。

### 6.2 内存中的短期窗口

CPU、内存和温度的短期窗口只放内存，不落盘。App 重启后从头积累。CLI 对不足的窗口返回 `insufficient_window`。

### 6.3 落盘文件

目录是 `~/Library/Application Support/MoleMonitor/`。文件权限是 0600。

| 文件 | 内容 | 写入与保留 |
|---|---|---|
| `disk-YYYY-MM.ndjson` | 每 15 分钟一行：磁盘样本、网络累计字节、开机时间 | 追加写，不调用 fsync。按月分文件，保留 2 个月 |
| `status.json` | 当前完整状态 | 写临时文件后 `rename` 原子替换，只保留 1 份 |
| `trend.json` | 2 小时趋势缓冲，重启后恢复 | 每 5 分钟写临时文件后 `rename` 原子替换，只保留 1 份 |
| `config.json` | 可选。忽略列表，阈值覆盖 | 用户手动编辑，工具只读 |
| `alert-state.json` | 磁盘通知状态 `DiskAlertState`：上次增长通知的字节数与等级，上次低空间通知的时间 | 状态变化时写临时文件后 `rename` 原子替换。启动时读回。该文件存在也是 `isFirstLaunch` 判据之一 |

第一版不做耗电小时汇总文件，也不做事件日志。

磁盘行示例：

```json
{"v":1,"t":"2026-10-11T08:15:00Z","src":"timer","ok":true,"vol":"/System/Volumes/Data","total":994662584320,"avail_important":412310421504,"avail":398123450368,"used":582352162816,"net_rx":812345678901,"net_tx":123456789012,"boot":"2026-10-08T01:02:03Z"}
```

- `src` 取值：`launch`、`timer`、`wake`、`panel`。
- `ok:false` 的行表示读取失败。计算增长量时跳过该行，不当作 0。
- 启动时读取最近 35 天的行。损坏的行跳过并计数。
- 估算写盘量约 4.5 MB/天（主要来自 `status.json`）。设计目标：状态卡关闭时 CPU 均值 ≤ 0.1%，RSS ≤ 30 MiB。目标待 Mac 实测。

## 7. 网速与流量

网速与流量属于次要区，来源是用户需求 R9。

### 7.1 网速

1. 状态卡打开时，每 2 秒读一次网卡累计字节计数器，做差得到网速。
2. 状态卡关闭时不采集，并清空缓冲。
3. 网速不进菜单栏，不做网络异常通知。

已实现的范围是“显示与实时曲线”：实时卡里的上下行折线，窗口 60 秒，只放内存。网速的判定规则和通知都没有实现，也不在计划内。

### 7.2 避免 VPN 双算

| 规则 | 内容 |
|---|---|
| 计入的名称前缀 | `en`（Wi-Fi 与有线）、`pdp_ip`（蜂窝） |
| 排除的名称前缀 | `lo`、`utun`、`awdl`、`llw`、`bridge`、`ap`、`gif`、`stf`、`anpi`、`vmenet` |
| 计数器 | 64 位，来自 `sysctl NET_RT_IFLIST2`，避免 32 位回绕 |

共享或桥接场景可能重复计数。这一项列为验证项 V22。

### 7.3 流量消耗

状态卡显示"今天"和"近 5 天"的流量。

1. 每 15 分钟，把累计字节和开机时间写入磁盘记录的同一行。
2. 计算流量时，按相邻两行的差值累加。
3. 如果开机时间变化，说明计数器已重置。此时从该行起分段累加，不与上一行做差。

## 8. CLI

### 8.1 形态

构建时多编一个只链接 Foundation 的小二进制，名称是 `molemonitor-cli`。它放在 App 包内的 `Contents/Helpers/`。App 可执行文件叫 `MoleMonitor`。macOS 默认文件系统不区分大小写，所以不能把 CLI 命名为 `molemonitor`，否则两者同名冲突。CLI 走这个二进制，不加载 AppKit。目标启动到返回 ≤ 20 ms。目标待 Mac 实测，做不到再放宽。构建脚本不自动安装 CLI。

### 8.2 子命令

| 命令 | 输出 |
|---|---|
| `--status` | 完整 JSON |
| `--status --brief` | 一行中文 |
| `--disk-history [--days N]` | 每天一行：日期，当天最低与最高真实已用，日增长 |
| `--schema` | 字段说明，含口径说明 |
| `prompt [--topic T]` | 排查提示词。T 为 `disk`、`memory`、`cpu`、`thermal`、`power`、`network`。`--apps` 或 `--no-apps` 强制包含或隐藏 App 名称 |
| `--version`、`--help` | 文本 |

### 8.3 字段结构

每个数值字段都是 `{value, unit, status, sampled_at}`。只有 `status` 为 `ok` 时，`value` 才有意义，其他情况 `value` 为 `null`。这样测得的 0 和取不到的值不会混淆。

| `status` 值 | 含义 |
|---|---|
| `ok` | 测得的值，可以是 0 |
| `collecting` | 刚启动或刚唤醒，尚无第一个样本 |
| `insufficient_window` | 有样本，但窗口覆盖不足 |
| `missing` | 设备没有该传感器，或芯片的传感器表未验证 |
| `failed` | 读取出错 |
| `stale` | 样本比允许时间旧 |
| `not_applicable` | 不适用，例如台式 Mac 的电池 |

- `active_alerts` 的每一项含 `type`、`subject`、`level`、`since`、`message`、`agent_hint`。
- JSON 不输出任何"已恢复"字段。
- 第一版 JSON 不输出 `usage_15m`、`wired`、`compressed` 和 `basis` 文本块。口径说明放进 `--schema`。
- 例外：磁盘 `growth` 对象在有 2 条以上样本时，即使 `status` 为 `insufficient_window`，也给出 `bytes`，该值是下限。

### 8.4 退出码

| 退出码 | 含义 |
|---|---|
| 0 | 数据新鲜：`status.json` 年龄 ≤ 420 秒，且写入进程仍在运行 |
| 2 | 参数错误 |
| 3 | 数据过期，或 App 没运行。CLI 仍输出最后的 JSON |
| 4 | 没有状态文件 |

### 8.5 App 没运行时

1. 如果 `status.json` 存在，CLI 输出它的内容。
2. 磁盘增长量由 CLI 从磁盘 NDJSON 重新计算，因为历史在文件里。
3. 其他项的 `status` 标为 `stale`。
4. 如果没有任何文件，CLI 输出"MoleMonitor 尚未运行过"，退出码 4。
