# MoleMonitor 面板 v2 设计

本文档定义面板 v2 的完整设计：菜单栏图标、英雄区比熊动画、分项区、侧栏明细、异常区和一键复制提示词。本文档取代 [DESIGN.md](DESIGN.md) 中第 13 章列出的章节和门禁。没有被列出的旧章节继续有效。

- 状态：设计稿，待甲方验收。
- 日期：2026-10-12。
- 范围：Mac 应用 `Sources/App/`、核心逻辑 `Sources/Core/`、CLI `Sources/cli/`、CI 门禁 `scripts/ci_acceptance.py`。
- 产品边界：见 [PROJECT.md](PROJECT.md)。本文档不改变“只检测、只预警、只读”的边界。

## 0. 来源与术语

### 0.1 用户原话（设计依据）

本设计以下面的用户原话为依据。各章的决定都可以追溯到这些原话。

| U2 | 那既然我们的这个定位是监测加问题提醒，那就是问题优先原则！我们要突出的是状态和问题！没问题的就统统靠后 | 后续决定 |
| U3 | 所有的这些东西，都应该你来定，你按照获奖标准来出，我只是作为你的甲方来验收，明白吗 | 后续决定 |
| U4 | 我说的验收还包括交互、丝滑动效和优雅的现代化UI | 后续决定 |
| U5 | 面板可以搞得酷一些，动态图表那种 | 后续决定 |
| U6 | 当前这个设计还是有很大的问题，这个静态的小狗完全体现不出我想要的可爱、有趣的特色，现在这种状态栏太多了，你明白吗，我们要搞出一些有趣的点子出来，另外就是当前这个面板、信息的展示、悬停的交互、按钮的设置，全都非常的不产品，一点都不专业！我希望的是，首先要有一个状态位置，通过状态栏icon提现初步的状态；然后面板一进来，通过小狗的动作动画、消息气泡这种交互，告诉机主当前状态，然后是一个分项区域，展示各个分项的状态、数值、悬停后在侧面打开分享单独的明细或者app排行，这样交互不好吗？一个异常告警，有无异常或者异常记录等，再提供一个一键复制优化提示词的功能即可，这个文案也要考虑考虑，信息排版、文字排版、图表交互这些统统都要好好设计一下，可以接受一定程度的运行资源占用，合理范围即可，尽量优化 | 2026-10-12 |

其他已定事实：狗是比熊。CPU 用“速度”类比。目标是 Apple Design Award 的水准。

### 0.4 数值单位

- 尺寸单位是 pt。截图和位图单位是 px，@2x 时 1 pt = 2 px。
- 时长单位是 ms 或 s。
- 帧率单位是 fps。步频单位是 Hz（步每秒）。
- 气泡字数用“宽度单位”：一个全角字符（中文、全角标点）计 1，一个半角字符（字母、数字、半角空格、半角标点）计 0.5。

## 1. 目标与不做

### 1.1 目标

面板 v2 要让机主在 3 秒内知道三件事：电脑现在好不好，哪一项有问题，下一步做什么。

| 编号 | 目标 | 可测的标准 |
|---|---|---|
| G1 | 菜单栏图标给出初步状态 | 五态在 1x 菜单栏可以互相区分（第 9 章） |
| G2 | 比熊用动作和气泡说出当前状态 | 打开面板后 300 ms 内动作与状态一致，气泡 ≤24 宽度单位（第 4 章） |
| G3 | 问题优先（U2） | 问题分项置顶并染色，正常分项灰阶，全绿时只有一处绿色（第 5 章） |
| G4 | 明细在侧面打开（U6） | 悬停 350 ms 或点击打开侧栏，同一窗口，≤250 ms（第 6、10 章） |
| G5 | 异常可见，异常可追溯 | 无异常只占一行，异常记录保留 30 天（第 7 章） |
| G6 | 一键复制提示词 | 底部只有一个主按钮，复制后 100 ms 内有反馈（第 8 章） |
| G7 | 丝滑与轻量（U1、U4、U6） | 面板打开 60 秒进程 CPU ≤3%（真机），关闭后无高频定时器（第 11 章） |

### 1.2 不做

下表的项目不做。后续工作包也不得加入。

| 不做 | 理由 |
|---|---|
| 清理、删除、卸载、结束进程 | 产品只读。清理由用户的 Agent 调用 Mole CLI |
| sudo、特权 helper、SMC 写入、风扇控制 | 红线，见 [AGENTS.md](../AGENTS.md) |
| 每应用耗电排行 | 红线。macOS 没有可靠的公开每应用耗电读数 |
| 用 CPU 使用率估算耗电 | 红线。估算会误导用户 |
| 每 App 网络排行 | 没有公开接口。见 6.5 |
| 饭盆、骨头、背包、表情包等第二套隐喻 | 一个隐喻更好懂。见 4.1 |
| 设置窗口、偏好页 | 选项只有 3 个，放在“…”菜单 |
| 菜单栏图标持续动画 | 菜单栏动画会分散注意力，也会持续耗电 |
| 实时点落盘 | 2 秒实时点只在内存中，关闭面板即清空 |

### 1.3 从现状删除的元素（回应 U6“状态栏太多”）

| 删除的元素 | 现状位置 | 替代 |
|---|---|---|
| 正常项折叠行 | 问题卡下方 | 6 行分项全部显示，正常项灰阶 |

## 2. 信息架构与线框

### 2.1 信息顺序

面板从上到下按“状态 → 分项 → 异常 → 行动”排列。菜单栏图标在面板之前给出初步状态。

| 顺序 | 区域 | 回答的问题 | 首屏可见 |
|---|---|---|---|
| 0 | 菜单栏图标 | 有没有问题，多严重 | 是（面板关闭时） |
| 1 | 英雄区 | 现在怎么样（一句话） | 是 |
| 2 | 分项区 | 哪一项，数值多少，趋势如何 | 是 |
| 3 | 异常区 | 有几条异常，持续多久，过去有没有 | 是 |
| 4 | 底部 | 下一步做什么 | 是 |
| 5 | 侧栏 | 这一项的明细和 App 排行 | 按需打开 |

面板不滚动。侧栏内部可以滚动。

### 2.2 宽度与网格

主列宽 352 pt。现状宽 328 pt。主列加宽 24 pt。理由：分项行要同时放两行文字、88 pt 大数值和 84 pt 迷你曲线。在 328 pt 内，迷你曲线只剩 60 pt，读不出趋势。

| 参数 | 值 |
|---|---|
| 主列宽 | 352 pt |
| 左右内边距 | 16 pt |
| 内容宽 | 320 pt |
| 网格 | 4 pt。所有尺寸和间距是 4 的倍数，文字基线除外 |
| 侧栏宽 | 320 pt（含 1 pt 分隔线和 16 pt 内边距，内容 287 pt） |
| 侧栏展开后面板总宽 | 672 pt |
| 窗口圆角 | 12 pt |
| 静态预览宽 | 704 px（主列 @2x）、1344 px（展开侧栏 @2x） |

### 2.3 高度公式

| 区块 | 高度 |
|---|---|
| 顶部内边距 | 12 pt |
| 英雄区 | 152 pt |
| 英雄区到分项区 | 8 pt |
| 分项区 | 6 行 × 40 pt = 240 pt。台式机没有电池：5 行，200 pt |
| 分项区到异常区 | 12 pt |
| 异常区，无异常 | 36 pt |
| 异常区，有异常 | 标题 28 pt + 每条 44 pt，最多 3 条 |
| 异常区到底部 | 12 pt |
| 底部 | 40 pt |
| 底部内边距 | 12 pt |

| 异常条数 | 总高（笔记本） | 总高（台式机） |
|---|---|---|
| 0 | 524 pt | 484 pt |
| 1 | 560 pt | 520 pt |
| 2 | 604 pt | 564 pt |
| 3 条或更多 | 648 pt | 608 pt |

规则：

1. 面板高度只在异常条数变化时改变。
2. 刷新数值、悬停、打开侧栏都不改变高度。
3. 高度改变时，顶边固定，底边移动，动画 220 ms。RM 时直接改变，无动画。
4. 高度改变只在面板打开期间发生。面板在下一次打开时直接用新高度。

### 2.8 四种数据状态的区分

| 状态 | 状态点 | 数值 | 迷你曲线 | 说明行 |
|---|---|---|---|---|
| 测得 | 按等级 | 实际值，零值显示“0%”或“0 B/s” | 实线 | 正常说明 |
| 采集中 | 空心圆 | 有值显示值，无值显示“采集中” | 虚线占位 | “正在采集” |
| 过期 | 虚线圆 | 最后值，灰色，前面加时刻 | 灰色实线，末端截止 | “停在 13:20” |
| 缺失 | 横线“—” | “—” | 无 | 缺失原因，例如“这台 Mac 没有电池” |
| 失败 | 叹号圆 | “读取失败” | 无 | 失败原因，例如“SMC 不可用” |

测得的零值与缺失必须看起来不同：零值有数字，缺失是“—”。

## 3. 视觉语言

### 3.1 原则

1. 颜色只表示问题。正常分项不用彩色。
2. 数值是视觉重心。名称和说明退后。
3. 一种信息只用一种编码方式加一种冗余方式：形状加颜色。色盲用户靠形状区分。
4. 动效表示因果：打开、展开、复制成功。动效不做装饰。比熊是唯一的持续动效。

### 3.2 字体层级

全部使用系统字体 SF Pro。数值使用等宽数字（`.monospacedDigit()`）。

| 令牌 | 用途 | 字号 / 字重 | 行高 | 颜色令牌 |
|---|---|---|---|---|
| `type.bubble` | 气泡正文 | 13 pt / medium | 18 pt | `text.primary`，问题数字 `text.danger` 或 `text.warning` 加 semibold |
| `type.bubbleSub` | 气泡下方“还有 N 项需要处理” | 11 pt / regular | 14 pt | `text.secondary` |
| `type.rowName` | 分项名称 | 13 pt / medium | 16 pt | `text.primary` |
| `type.rowNote` | 分项说明 | 11 pt / regular | 14 pt | `text.secondary` |
| `type.rowValue` | 分项大数值 | 17 pt / semibold，等宽数字 | 20 pt | 正常 `text.primary`，问题按等级 |

## 4. 英雄区：比熊动作与气泡

### 4.1 一个隐喻：比熊的身体就是这台电脑

比熊只用自己的身体表现电脑状态。设计不加饭盆、骨头、背包或表情包。唯一的道具是比熊的窝，它表示磁盘。

| 电脑状态 | 比熊的表现 | 理由 |
|---|---|---|
| CPU 负载 | 奔跑的步频，连续变化 | 用户已定：CPU = 速度 |
| 温度高 | 黄：汗珠、呼吸加快。红：趴地喘气 | 热了就喘，人人都懂 |
| 内存紧 | 黄：身体下沉 2 pt，步子变慢。红：背上压着一堆杂物，慢慢走 | 内存满 = 背着东西跑不动 |
| 磁盘紧或暴涨 | 窝里堆满东西，窝出现在舞台左下 | 磁盘 = 家里的存储空间 |
| 耗电偏快 | 累了趴下 | 电量是体力 |
| 夜间（22:00–6:00）且无问题 | 舞台变暗，比熊蜷着睡觉 | 陪伴感 |
| 采集中 | 低头嗅地面 | 正在“闻”数据 |
| 数据过期 | 坐着发呆，身体去色 | 不知道发生了什么 |

情绪幅度控制在“生活观察”的程度。比熊不哭、不晕倒、不冒烟、不出现夸张表情符号。

| 优先级 | 条件 | 基础动作 | 叠加效果 |

| 1 | 数据过期 | `sit_gray` | 全身去色 |

| 2 | 温度红 | `pant_lie` | 汗珠 |
| 3 | 内存红 | `burdened_walk` | 步频按 CPU 计算，上限为 `walk` 的 1.0 Hz |
| 4 | 耗电黄或红，且 CPU < 40% | `tired_lie` | 无 |
| 5 | 一次性动作正在播放 | 该一次性动作 | 保留叠加 |
| 6 | 夜间，无问题，CPU < 20% | `sleep_curl` | 夜间舞台 |
| 7 | 其他情况 | CPU 步态（4.5） | 见下行 |

| 条件 | 叠加效果 | 实现 |
|---|---|---|
| 磁盘黄 | 窝出现，窝里半满（`bed_some`） | 静态位图 |
| 磁盘红 | 窝出现，窝里堆满（`bed_full`） | 静态位图 |

| 内存黄 | 身体下沉 2 pt，步频 × 0.8，地面平移 × 0.8 | 程序化 |

问题期间不播放空闲小动作和彩蛋。点击比熊仍然播放 `wag`，因为用户的操作必须得到回应。

### 4.5 速度：步频随 CPU 连续变化

输入 s 是系统总 CPU 使用率（0–100%），来自 2 秒实时采样。

1. 打开面板时，s 直接取第一个实时值，不平滑。
2. 面板打开期间，s 用指数平滑，τ = 6 s。
3. 步频 f(s) 是分段线性函数，节点如下：

| s（CPU） | 10% | 40% | 80% | 100% |
|---|---|---|---|---|
| f（Hz） | 0.70 | 1.30 | 2.08 | 3.00 |

4. 步态按 s 选择，阈值与迟滞沿用现有 `DogArtSelector`：

| 步态 | 进入 | 退出 | 自然步频 |
|---|---|---|---|
| 躺 `lie_idle` | s < 7% | s ≥ 10% | —（呼吸固定 1.5 s） |
| 走 `walk` | s ≥ 10% | s < 7% | 1.0 Hz |
| 小跑 `trot` | s ≥ 40% | s < 34% | 1.6 Hz |
| 冲刺 `sprint` | s ≥ 80% | s < 72% | 2.4 Hz |

5. 播放倍率 = f(s) ÷ 当前步态的自然步频。例：s = 60% 时 f = 1.69 Hz，`trot` 倍率 1.06，帧率 13.5 fps。
6. 每次采样，倍率变化 ≤0.25。这一条防止跳变。
7. 冲刺帧率上限 18 fps（s = 100%，倍率 1.25）。
8. 地面纹理平移速度 = 24 pt × f(s)，即 s = 100% 时 72 pt/s。
9. 步态切换保留现有规则：同一步态最短保持 4 s，10 s 内最多切换 2 次。

因为 f(s) 在步态切换点两侧连续，所以步频在切换时不跳变，只有步态外形改变。

### 4.6 动作过渡

| 从 | 到 | 方法 |
|---|---|---|
| 走、小跑、冲刺之间 | 走、小跑、冲刺 | 等到当前动作的下一个着地帧，直接切到目标动作的着地帧 0 |
| 躺类（`lie_idle`、`pant_lie`、`tired_lie`） | 站类 | 播放 `stand_up`，再进入目标 |
| 站类 | 躺类 | 倒放 `stand_up`（`lie_down`），再进入目标 |
| 任何动作 | `sit_gray`、`sniff`、`sleep_curl`、`burdened_walk` | 交叉淡变 160–200 ms（`sleep_curl` 400 ms） |
| 一次性动作结束 | 原基础动作 | 原动作从帧 0 继续，交叉淡变 120 ms |

如果一次性动作播放期间状态变化，那么一次性动作先播完，然后进入新的基础动作。`notice` 例外：它马上打断空闲小动作。

### 4.7 空闲小动作

空闲小动作只在“无问题、面板打开、比熊在 `lie_idle` 或 `walk`”时出现。

| 规则 | 值 |
|---|---|
| 第一次出现 | 打开面板后 8–14 s（随机） |
| 之后间隔 | 18–30 s（随机） |
| 抽取 | `yawn` 40%、`scratch` 35%、`head_turn` 25%，不连续重复同一个 |
| 调度方式 | 前一个动画的 `CAAnimation` 结束回调安排下一个，不用定时器 |

### 4.8 摸狗与彩蛋

命中检测用当前帧的 alpha 通道：alpha ≥0.3 的像素算“摸到比熊”。

| 操作 | 判定 | 回应 |
|---|---|---|
| 点击比熊 | 按下到抬起 < 300 ms，位移 < 4 pt | 播放 `wag`，3 颗爱心从头部上浮 24 pt，900 ms 淡出，气泡换成摸狗文案 |
| 3 s 内点击 5 次 | 计数 | 气泡“别摸啦，我在站岗”，播放 `head_turn` |
| 长按比熊 | ≥600 ms | 播放 `roll`，气泡“肚子给你，轻点挠” |
| 悬停比熊 | 停留 1.2 s | 播放 `head_turn`，每 30 s 最多一次 |
| 一次会话摸 10 次 | 会话内计数 | 气泡“今天第 10 次摸我啦” |
| 早晨 6:00–10:00 第一次打开 | 当天第一次 | 气泡“早上好，昨晚没有异常”（只在昨晚无异常记录时） |
| 周五 18:00–22:00，无问题，CPU < 20% | 每周一次 | 气泡“周五了，电脑也想下班” |

规则：

1. 摸狗文案显示 2.5 s，然后回到状态文案。
2. 有问题时不出现彩蛋文案。点击仍然 `wag` 和爱心，但气泡保持问题文案。
3. 问题恢复时不播放“恢复”庆祝动画。比熊直接回到对应步态。理由：恢复不需要打扰用户。
4. 摸狗计数只在内存中，不落盘。

### 4.9 夜间与 RM

夜间：

1. 夜间为本地时间 22:00–6:00。
2. 夜间舞台用 `stage.night`，显示月亮和 3 颗星。分项区、异常区的颜色不变。
3. 夜间无问题且 CPU < 20% 时，比熊播放 `sleep_curl`。气泡“夜深了，一切正常，晚安”。
4. 夜间 CPU ≥ 20% 时，比熊按 CPU 步态活动。气泡“这么晚还在忙，CPU {P}%”。
5. 夜间有问题时，问题动作优先。

RM 打开时：

| 元素 | RM 下的行为 |
|---|---|
| 基础动作 | 只显示静止帧，不循环 |
| 地面平移、呼吸、汗珠抖动 | 停止 |
| 一次性动作、空闲小动作、爱心 | 不播放 |
| 气泡 | 直接出现，无弹出缩放 |
| 动作切换 | 静止帧之间淡变 160 ms |
| CPU 速度的表达 | 静止帧选用步态对应的帧，气泡文字给出 CPU 数值 |

### 4.10 气泡规则

1. 气泡长度 ≤24 宽度单位（0.4 节）。
2. 气泡最多 2 行，13 pt medium，行高 18 pt，宽 ≤192 pt（内容 172 pt）。
3. 有问题时，气泡必须包含一个证据数字。数字用 semibold 加等级颜色。
4. 多项问题时，气泡讲排序第一的问题，副行写“还有 N 项需要处理”。
5. 气泡在以下时刻弹出：打开面板、问题集合改变、复制、摸狗。其他时刻只替换文字，不弹出。
6. 数值刷新（每 2 s）不改变气泡文字。气泡文字最多每 30 s 更新一次数字，问题集合改变时马上更新。
7. 文案不用“您”。比熊用第一人称“我”，称呼机主为“你”。

### 5.2 排序与着色（问题优先，U2）

1. 问题分项（黄、红）排在最前。问题之间按现有 `ProblemOrder` 排序：先红后黄，同级按固定优先级 温度 > 内存 > 磁盘 > 耗电 > CPU，开始时间相差 60 s 以内视为同时。

### 5.4 内存压力百分比

| 项目 | 规定 |
|---|---|
| 来源 | `sysctl kern.memorystatus_level`，系统可用内存百分比 |
| 公式 | 压力百分比 = 100 − `kern.memorystatus_level`，取整数，夹在 0–100 |
| 等级 | 仍以 `kern.memorystatus_vm_pressure_level` 为准：1 正常，2 警告，4 严重。不由百分比阈值推算 |
| 采样位置 | `Sources/App/SystemSampler.swift`。在现有 30 秒慢速采样中读取。面板打开时，也在现有 2 秒实时采样中读取。不新增定时器 |
| Core 字段 | `CurrentReadings.memoryPressurePercent: Int?`、`TrendPoint.pressurePercent: Int?`（JSON 键 `pp`）、`HealthItemStatus.pressurePercent: Measured<Int>?` |
| 曲线 | 进入 2 小时环形缓冲（粗段 30 s）和细段（2 s），随 `trend.json` 保存 2 小时。5 分钟汇总写入 `rollup` 文件（12.2） |
| 读不到 | sysctl 失败或值不在 0–100：字段为 nil。界面显示“—”，状态为“缺失”。不显示 0 |
| 说明文字 | 侧栏在压力图下写：“压力百分比是近似读数，颜色以系统压力档位为准。” |
| 测试 | Core 单测用固定输入：level 77 → 23%，level 0 → 100%，level 100 → 0%，level −1 或 101 → nil，nil → “—” |
| 真机待验 | 在 Mac 上对比 `memory_pressure` 命令最后一行“System-wide memory free percentage”与本读数，并与“活动监视器”的压力图对照 |

> **注意**：`kern.memorystatus_level` 没有 Apple 官方文档。Firefox 与 Chromium 源码称它为非官方读数。百分比不等于“活动监视器”的颜色判定。因此界面颜色只跟随系统压力档位。

### 6.3 容量区：总容量、已用、可用

用户 2026-10-12 原话：「磁盘、内存这种用更合适的排版展示出总容量、已用、可用」。容量区放在侧栏统计行下方，只用于磁盘和内存。

版式：

```text
┌ 287 pt ─────────────────────────────────────┐
│ ███████████████████▓▓▓▓░░░░░░░░░░░░░░░░░░░░ │ 分段条 8 pt，圆角 4 pt
│ 12                                          │
│ 总容量          已用           可用           │ 10 pt 标签
│ 995 GB        593 GB        402 GB         │ 15 pt 数值，等宽数字，各栏右对齐
│ ■ 已用  ▓ 可清除 21 GB  ░ 立即可用              │ 10 pt 图例
└─────────────────────────────────────────────┘
```

| 项目 | 规定 |
|---|---|
| 三栏宽度 | 各 95 pt，栏内数值右对齐 |
| 单位 | 同一组三个数字用同一单位 |
| 精度 | 磁盘：整数 GB。总容量 ≥10000 GB 时三栏改用 TB，2 位小数。内存：GB，1 位小数 |
| 进制 | 磁盘用十进制 GB（10^9 B），与“访达”一致。内存用二进制 GB（2^30 B），与“活动监视器”一致 |
| 和的关系 | 显示的已用 + 显示的可用 = 显示的总容量。程序先取整总容量和已用，再用两者之差得到可用 |
| 缺失 | 任何一个原始值缺失：三栏都显示“—”，分段条显示灰色虚线框，脚注写原因 |

磁盘口径：

| 栏 | 计算 | Core 字段 | 现状 |
|---|---|---|---|
| 总容量 | `volumeTotalCapacity` | `DiskItem.total` | 现有可用 |
| 已用 | 总容量 − `volumeAvailableCapacityForImportantUsage` | `DiskItem.used` | 现有可用 |
| 可用 | `volumeAvailableCapacityForImportantUsage` | `DiskItem.availableImportant` | 现有可用 |
| 其中可清除 | 重要用途可用 − `volumeAvailableCapacity` | `DiskItem.purgeableEstimate` | 现有可用 |

1. 已用不含可清除空间（快照、系统缓存）。因此已用 + 可用 = 总容量，没有差额。
2. 可清除空间是“可用”的一部分。分段条把“可用”分成两段：可清除（斜纹）和立即可用（浅色）。
3. 脚注：“可用含 21 GB 可清除空间。系统需要时会自动释放它。”
4. 主列的分项行只用 `CurrentReadings.diskAvailable`。侧栏需要总容量、已用和可清除：`CurrentReadings` 需新增 `diskTotal`、`diskUsed`、`diskPurgeable` 三个字段，由 `StatusExtras` 和 `Engine` 从 `DiskItem` 填入。

内存口径：

| 栏 | 计算 | 现状 |
|---|---|---|
| 总容量 | `hw.memsize` | 现有可用：`CurrentReadings.physicalMemory` |
| 已用 | App 内存 + 联动内存 + 压缩内存 | 需新增 |
| App 内存 | (`internal_page_count` − `purgeable_count`) × 页大小 | 需新增 |
| 联动内存 | `wire_count` × 页大小 | 需新增 |
| 压缩内存 | `compressor_page_count` × 页大小 | 需新增 |
| 可用 | 总容量 − 已用（含文件缓存和空闲页） | 需新增（计算值） |
| swap 已用 | `vm.swapusage` | 现有可用：`CurrentReadings.swapUsed` |

1. 页面计数来自 `host_statistics64(HOST_VM_INFO64)`。页大小来自 `vm_kernel_page_size`。读取位置与压力百分比相同（5.4），不新增定时器。
2. Core 需新增 `MemoryBreakdown { app, wired, compressed, total }`（单位字节，可为 nil）与计算属性 `used`、`available`。
3. 这个口径与“活动监视器”的“已使用内存”同构：App 内存 + 联动内存 + 被压缩。数值可能相差几百 MB，因为两者采样时刻不同，而且“活动监视器”的 App 内存算法没有公开。脚注写：“已用 = App 内存 + 联动内存 + 压缩内存，与活动监视器口径相近。”
4. 分段条分 4 段：App 内存、联动内存、压缩内存、可用。可用含文件缓存，因为系统可以随时收回。
5. swap 不画进分段条。swap 在统计行显示。

分段颜色：

| 段 | 正常 | 分项有问题 |
|---|---|---|

### 6.5 App 排行口径

| 排行 | 指标 | 窗口 | 来源 | 现状 |
|---|---|---|---|---|
| CPU 占用前 5 | CPU %，单核满载 = 100% | 实时（2 s）与近 5 分钟均值 | `proc_pid_rusage` 差值 | 现有可用 |
| 内存占用前 5 | 物理占用（`ri_phys_footprint`） | 实时 | `proc_pid_rusage` | 现有可用 |
| 磁盘写入前 5 | 写入字节（`ri_diskio_byteswritten` 差值） | 近 5 分钟 | `proc_pid_rusage` RUSAGE_INFO_V4 | 需新增 |
| 阻止睡眠的 App | 断言类型（防止系统睡眠 / 防止显示器睡眠） | 实时 | `IOPMCopyAssertionsByProcess` | 需新增 |

排行规则：

1. 同一 App 的多个进程按 bundle 合并，显示 App 名和图标（16 pt）。
2. 每行 28 pt：图标 16 pt、名称 13 pt、右侧数值 13 pt 等宽数字、数值下方 2 pt 比例条。
3. 排行只显示 App 显示名，不显示完整进程参数。
4. 排行每 4 s 更新一次，行顺序变化用 `motion.reorder`。
5. 不做每 App 网络排行。理由：macOS 没有公开的每进程网络计数接口。每 4 s 启动一次 `nettop` 子进程的成本太高，而且违反“极其轻量”（U1）。
6. 不做每应用耗电排行，不以 CPU 估算耗电。这是红线。

### 8.3 提示词原则

| 编号 | 原则 |
|---|---|
| P1 | 只读诊断先行。提示词要求 Agent 先只读诊断，再给建议 |
| P2 | 证据带数字。每个问题至少有一个数字和单位，例如“5 天 +314 GB” |
| P3 | 清理交给用户的 Agent。Agent 可以调用 Mole CLI，但 Mole 清理只用 `--dry-run` 预览 |
| P4 | 不让 Agent 自行改动。任何改动前，Agent 列清单并等用户确认 |
| P5 | 长度 ≤3000 字符（Swift `String.count`） |
| P6 | 标题就是问题。Agent 看第一行就知道要解决什么 |
| P7 | 不含隐私：家目录写成 `~`，不含序列号、完整进程参数、凭据。现有脱敏规则 S1–S8、T1–T13 保留 |

安全规则保留旧设计的 7 条，内容不放宽：第 1–6 条在提示词第 4 节，第 7 条“回复：结论 → 证据 → 下一步”在第 2 节。设计评估过“用户确认后允许 Agent 运行非 dry-run 的 Mole 清理”，决定不改。理由：真正的删除应当由用户在终端里亲自确认，这是本产品“只读”承诺的一部分。

### 8.5 多项问题的合并规则

1. 问题按 5.2 的顺序排列。
2. 第 1 个问题：写完整排查步骤。
3. 第 2 个问题：如果总长度 ≤3000，那么写完整步骤。否则只写前 2 步。
4. 第 3 个及以后的问题：放在“3.N 其余问题（各做第一步）”，每项只写第一条命令。
5. 第 5 节的指标表合并全部问题的指标，每个指标只出现一次。
6. App 表的列按第 1 个问题选择：磁盘问题用写入量，内存问题先列内存，CPU 和温度问题先列 CPU。

### 8.6 超长压缩顺序

如果提示词超过 3000 字符，那么按下面顺序逐级压缩，每一级之后重新计数：

| 级 | 操作 |
|---|---|
| L1 | App 表从 5 行减到 3 行 |
| L2 | 删除“近 7 天异常记录”行 |
| L3 | 第 2 个问题的步骤减到前 2 步 |
| L4 | 第 3 个及以后的问题合成一行：“其余问题：CPU（黄）、温度（黄）。先完成上面的步骤。” |
| L5 | 每个口径行缩短为第一句 |
| L6 | 机器行只保留芯片和内存 |

第 0、1、2、4 节永远不压缩。如果 L6 之后仍然超过 3000，那么删除第 5 节。门禁 W20 检查：全部黄金样例 ≤3000，并且第 4 节逐字存在。

### 8.7 文案原则

1. 提示词用机主的口吻，称呼 Agent 为“你”。
2. 一句一事。步骤用祈使句：“运行 …”“列出 …”。
3. 每条命令写完整，不写别名。CLI 写完整路径。
4. 有截断风险的命令必须带截取，例如 `| head -n 15`、`| tail -n 200`。
5. 每节标题带编号，便于 Agent 在回复中引用。
