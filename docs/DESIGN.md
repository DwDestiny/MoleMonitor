# 状态卡、比熊与提示词重设计规格

本文件是 MoleMonitor 表现层的重设计规格。工程师按本文件实现菜单栏图标、状态卡、比熊动画、趋势曲线、占用 App 与“复制给 Agent”提示词。数据层沿用 [PROJECT.md](PROJECT.md) 第 3 节（健康模型）与第 6 节（采样）的原生低频设计，本文件只补充表现层需要的数据。

本文件不写产品代码。实现时，本文件与 [PROJECT.md](PROJECT.md) 冲突的地方以本文件为准，并在实现提交中同步修订 PROJECT.md（修订清单见 [10.4](#104-对现有文档与规则的修订)）。

| 术语 | 定义 | 不使用的词 |

| 问题卡 | 问题模式下展开的那个问题项的卡片，含关键数字、证据曲线与证据列表 | 告警卡 |
| 问题行 | 问题模式下未展开的问题项，单行显示 | 告警行 |

| 趋势缓冲 | 常驻内存的环形缓冲，每 30 秒 1 个点，保留 2 小时 | 历史缓存 |
| 细段 | 状态卡打开期间每 2 秒 1 个点的数据，最多 5 分钟 | 实时段 |

| 提示词 | “复制给 Agent”写入剪贴板的中文文本 | prompt 文本、话术 |
| 专项 | 提示词中针对一类问题的排查段落：磁盘、内存、CPU、温度、耗电、网络 | 子模板 |
| 耗电 | 第 5 个健康项，由睡眠掉电与整机耗电异常两条规则判定。来自电池电量读数，不是每应用耗电 | 电池项、能耗 |
| 睡眠掉电 | 睡眠 ≥ 2 小时期间每小时下降的电量百分比，见 PROJECT.md 3.6 | 待机耗电 |

| 掉电速率 | 每小时下降的电量百分比，单位 %/小时 | 耗电量 |
| 档位 | 状态卡高度的 3 个固定值：332、560、620 pt | 尺寸档 |
| 证据区 | 问题卡内曲线之下的区域，高度有弹性，范围 68 至 114 pt | 详情区 |
| 手写路径 | 工程师手写的固定 Bezier 路径数据，是比熊外形的唯一来源 | 配方外形 |
| 部件变换 | `DogRig` 对部件施加的平移、旋转与缩放，不改变外形 | 骨骼动画 |
| 头像剪影 | 菜单栏图标的比熊正面头像 | 站姿剪影 |

## 1. 设计原则与品质标准

### 1.1 设计原则

原则按优先级排列。两条原则冲突时，编号小的原则优先。

**P1 问题优先。** 状态卡的区块顺序与视觉权重由 3 个量决定：是否有问题、问题多严重、问题已持续多久。指标的类别不决定位置。可检验的定义如下：

1. 有问题项时，最严重的问题项在灯列之后的第一个位置，占面积最大的区块（问题卡）。
2. 问题项按“健康等级降序 → 已持续降序 → 固定优先级”排序，规则见 [2.4](#24-问题排序规则)。
3. 正常项不使用颜色强调，不使用大字号，不占用问题卡。正常项压缩为灯列中的小灯和正常摘要行，或者放进折叠区。
4. 没有问题项时，状态卡进入安静模式。安静模式的高度比任何问题模式的高度小至少 200 pt。
5. “复制给 Agent”按钮紧跟在问题区块之后。按钮复制的提示词围绕当前最严重的问题项。
6. 菜单栏图标、比熊姿态、提醒列表与系统通知使用同一套排序规则。

**P2 两秒读懂。** 打开状态卡后 2 秒内，用户能回答 3 个问题：机器健康吗？哪一项有问题？问题持续多久了？英雄区的标题、灯列与“已持续”文字必须单独回答这 3 个问题。

**P3 轻量是功能。** 状态卡关闭时，App 只保留 1 个 30 秒定时器，不画任何帧。动画、细采样和进程高频扫描只在状态卡打开期间存在。全绿且状态卡关闭时，进程扫描周期是 300 秒。任一健康项为黄或红时，周期回到 180 秒。状态卡打开时为 4 秒。

**P4 有趣但克制。** 比熊是情绪化的信息载体，不是装饰。比熊的每个动作都对应一个数据含义（见 [4.4](#44-姿态集)）。菜单栏没有持续动画。

**P5 颜色不是唯一编码。** 每个健康等级都同时用 3 种方式表达：颜色、形状、文字。色盲用户和单色菜单栏下，等级仍然可辨。

**P6 诚实的数据。** 缺失、失败、过期、统计中与测得的 0 分开显示。不显示每应用耗电，不用 CPU 估算耗电。耗电项只来自电池电量读数。不显示“已恢复”。

**P7 反仪表盘。** 不使用圆形仪表、不使用大面积渐变、不使用多种强调色。全卡只有 1 个强调色（[2.6](#26-颜色令牌)）。背景使用系统 material。

### 1.2 品质标准（可检验）

“苹果设计奖水准”在本项目中拆成下面两组条目。第一组由 CI 回归门禁自动检查。第二组只能在真机上，由用户在最终验收时确认。

**CI 可检（每次提交检查，见 [9.2](#92-ci-回归门禁新增项)）：**

| 编号 | 条目 | 判定 |
|---|---|---|
| Q1 | 文字对比度 | 浅色与深色下，所有文字对背景的对比度 ≥ 4.5:1。灯与曲线等图形 ≥ 3:1 |
| Q2 | 大字号不溢出 | 字号放大到 1.25 倍时，每个文字槽位的最长字符串不超出槽位宽度 |
| Q3 | 减少动态效果 | 开启 Reduce Motion 后，2 秒内状态卡没有位移动画，比熊区域像素不变 |
| Q4 | 无障碍标签 | 每个按钮、灯、图表和问题卡都有非空的无障碍标签 |
| Q5 | 尺寸稳定 | 版面计划不变时，连续 10 次数据刷新后状态卡高度变化为 0 |
| Q6 | 问题优先排序 | 每个场景的区块纵向顺序与版面计划一致 |
| Q7 | 状态截图 | 安静、单项黄、单项红、耗电问题、多项、统计中、过期 7 个场景，各有浅色与深色、空数据与满数据截图 |
| Q8 | 冷启动首帧有曲线 | 预置趋势文件后，首次打开的第一张截图中曲线区域有线条像素 |
| Q9 | 无焦点环 | 打开状态卡后，没有按钮成为第一响应者，退出按钮周围没有焦点环像素 |
| Q10 | 关闭零成本 | 关闭 3 秒后只剩 1 个定时器，比熊视图已释放，帧计数停止 |

**真机可检（最终验收时用户本人确认，见 [9.3](#93-最终验收清单真机用户逐项确认)）：**

| 编号 | 条目 | 判定 |
|---|---|---|
| R1 | 动效手感 | 入场、展开、数字滚动没有卡顿或突跳 |
| R2 | ProMotion 平滑 | 120 Hz 屏幕上曲线滑入与弹簧动画平滑 |
| R3 | 图标清晰 | 菜单栏图标在浅色、深色、彩色壁纸下都能认出比熊和角标 |
| R4 | 能耗 | 活动监视器“能耗”页中 MoleMonitor 的“能耗影响”在状态卡关闭时显示为低（≤ 1.0） |
| R5 | 空闲 CPU | 状态卡关闭 1 小时，App CPU 均值 < 0.1% |
| R6 | 比熊可爱且可辨识 | 用户看一眼能认出比熊，并能区分趴、走、小跑、冲刺 |

## 2. 信息架构与布局

### 2.1 两种模式

状态卡只有两种模式。模式由问题项的数量决定。高度只有 3 档，见 [2.11](#211-高度策略)。

| 模式 | 条件 | 目标 | 高度 |
|---|---|---|---|
| 安静模式 | 问题项数量 = 0 | 让用户安心，然后离开。更小、更安静 | 332 pt |
| 问题模式（单问题） | 问题项数量 = 1 | 说清哪一项、多严重、持续多久，并给出下一步 | 560 pt |
| 问题模式（多问题） | 问题项数量 ≥ 2 | 同上，并列出其余问题项 | 620 pt |

### 2.2 线框

线框中的符号如下：

| 符号 | 含义 |
|---|---|
| `●` | 绿灯（实心） |

### 2.4 问题排序规则

问题项按以下 3 个键依次排序。前一个键相同时，才比较后一个键。

1. 健康等级：红在黄之前。
2. 已持续：已持续更长的在前。两个问题项的“问题开始时间”相差 < 60 秒时，视为相同。
3. 固定优先级：温度 > 内存 > 磁盘 > 耗电 > CPU。

固定优先级的理由：温度过高会降频并影响硬件，内存严重不足会让整机卡顿，这两项对机器健康的影响最直接。磁盘满会导致写入失败。耗电异常会缩短续航，并常常说明有程序阻止睡眠。CPU 高常常是用户主动的工作负载。

同一套顺序用于所有位置：

| 位置 | 使用的顺序 |
|---|---|
| 灯列（英雄区） | `ProblemOrder.all`：问题项在前，按上面 3 个键。正常项在后，按固定优先级 |
| 问题卡、问题行 | `ProblemOrder.problems` |
| 菜单栏角标、比熊气泡 | 排序第一的问题项 |
| 提示词、通知、提示文字 | `ProblemOrder.all` 或 `ProblemOrder.problems` |

排序有以下稳定性保证：

- 两个同等级问题项都在持续，所以它们的已持续同步增长，顺序不会自己翻转。
- 顺序只在等级变化、问题出现或问题消失时变化。等级有迟滞（见 PROJECT.md 3.1），所以顺序变化的频率很低。
- 顺序变化时，区块用淡入淡出切换，不做位移动画（见 [5.3](#53-逐处动效清单)）。

问题曲线的通用规则：

1. 横轴固定为“2 小时前”到“现在”。左下角与右下角各一个 10 pt 标签，颜色 `text.secondary`。
2. 纵轴不显示刻度。CPU 曲线纵轴固定 0 至 100%。swap 曲线纵轴为 0 至 max(当前最大值 × 1.3, 1 GB)。电量曲线纵轴固定 0 至 100%。
3. 进入阈值画成 1 pt 虚线（3,3），颜色 `text.secondary` 40%，线右端标注阈值数字。CPU 画 70% 与 90% 两条。电量曲线不画阈值线，因为耗电的阈值是速率。

**默认实现：两个 Chart。** 曲线不使用单个 Chart 重绘全部点。实现如下：

1. “粗段 Chart”画最近 2 小时的粗段点（每 30 秒 1 点），只在新粗点到达时重绘。
2. “细段 Chart”叠放在同一个绘图区上，只画最近 5 分钟的细段点（每 2 秒 1 点），每 2 秒重绘。
3. 两个 Chart 共用横轴域 [最近粗点 − 2 小时, 最近粗点 + 30 秒]。横轴域只在新粗点到达时变化。
4. 粗段 Chart 只画细段起点之前的点。细段 Chart 的第一个点是最近的粗点，让两段线连续。
5. 状态卡刚打开时细段为空，曲线完全由粗段 Chart 画出。
6. 迷你线（趋势条）只用粗段 Chart。

### 2.10 焦点环与退出按钮

上一版退出按钮的粗边框是焦点环。原因是状态卡打开时，系统把第一个按钮设为第一响应者。修复要求如下：

1. 状态卡显示后，在下一个主线程循环调用 `window.makeFirstResponder(nil)`，不让任何按钮成为第一响应者。
2. 所有按钮使用自定义 `ButtonStyle`，基于 `.plain`，加 `.focusEffectDisabled()`。
3. 退出、CLI、设置是图标按钮。默认无背景。悬停时显示 24 pt 圆形 `fill.hover`。按下时缩放到 0.94。
4. 用户按 Tab 键移动焦点时，焦点按钮显示 1.5 pt `accent` 圆角描边。描边由 `@FocusState` 驱动，只在键盘导航时出现。这一条保证键盘用户仍能看到焦点。
5. CI 检查 Q9 验证打开后的第一响应者不是按钮。

底栏按钮的行为（图标用 SF Symbols，不使用 `⌘_` 字样）：

| 按钮 | 形式 | 点击结果 |
|---|---|---|
| CLI | 图标按钮（`terminal`），弹出菜单 | 菜单项：“复制命令：一行状态”“复制命令：完整状态 JSON”“复制命令：排查提示词”。每项复制带完整路径的命令（家目录写 `~`） |
| 设置 | 图标按钮（`gearshape`），弹出菜单 | 菜单项：“提示词包含 App 名称”（勾选项，默认开）、“打开通知设置…”、“打开数据文件夹”、“关于 MoleMonitor”。不打开窗口 |
| 退出 | 图标按钮（`power`） | 退出 App，沿用现有退出流程（写 `status.json`） |

键盘快捷键：`⌘C` 复制主提示词，`⌘Q` 退出，`Esc` 关闭状态卡。

### 2.11 高度策略

状态卡高度只有 3 档。档位只由问题项数量决定，不依赖数值。数值变化永远不改变高度。

| 档位 | 条件 | 高度（pt） |
|---|---|---|
| 安静 | 问题项数量 = 0（含统计中、过期） | 332 |
| 单问题 | 问题项数量 = 1 | 560 |
| 多问题 | 问题项数量 ≥ 2 | 620 |

高度随问题项数量单调不减：0 项 332，1 项 560，2 项及以上 620。

**版面计划的计算：**

1. 取档位高度。最大高度 = min(档位高度, 屏幕可见高度 − 40) pt。
2. 按区块的标准高度排版（见 [2.5](#25-尺寸与间距)）。
3. 证据区高度 = 档位高度 − 其余区块高度（含间距与内边距）。证据区限制在 68 至 114 pt。
4. 如果证据区高度小于 68 pt，按以下顺序压缩，每步之后重新计算，达到 68 pt 即停止：
   1. 折叠行：先把“占用 App”并入“更多”，再把折叠行从 30 压到 26。
   2. 问题卡：改为紧凑问题卡（曲线 48，外壳 148）。
   3. 问题行：从 40 压到 36。
   4. 正常摘要行：隐藏。正常项仍在灯列中。
   5. 通知授权行：收入“更多”展开内容的首行，不单独占行。
5. 压缩顺序是先压折叠行，再压问题卡。每次压缩都不改变档位高度。
6. 如果余量大于 114 pt，多出的高度作为折叠区上方的留白。已定义的场景不会出现这种情况。

**高度的变化：**

1. 高度只在问题项数量跨档时变化：0 与 1 之间，1 与 2 之间。
2. 手风琴切换、折叠行展开或收起、通知授权行出现或消失，都不改变高度。
3. 展开折叠行时，展开内容占用中部区域，超出部分在中部区域内部滚动。展开时中部区域自动滚到被展开的折叠行顶部。
4. 高度只由 AppKit 设置 `popover.contentSize`，并设置 `popover.animates = true`。SwiftUI 内不做高度动画，内容固定顶部对齐。
5. 档位切换时，SwiftUI 内容只做淡入淡出（见 [5.3](#53-逐处动效清单)）。

各场景的计划高度（由 `PanelLayout.plan` 算出，Core 测试逐行断言）：

| 场景 | 档位 | 证据区 | 压缩步骤 |
|---|---|---|---|
| 安静 | 332 | — | 无 |
| 安静加授权行 | 332（内容 330，留白 2） | — | 合并折叠行 |
| 单项 CPU 黄 | 560 | 102 | 无 |
| 单项磁盘红或耗电黄 | 560 | 68 | 无 |
| 单项 CPU 黄加授权行 | 560 | 70 | 无 |
| 单项磁盘红加授权行 | 560 | 70 | 合并折叠行 |
| 2 项：内存与 CPU | 620 | 114 | 无 |
| 2 项：磁盘与 CPU | 620 | 80 | 无 |
| 3 项：磁盘、内存、CPU | 620 | 70 | 合并折叠行 |
| 4 项：磁盘、内存、耗电、CPU（线框 D） | 620 | 94 | 合并折叠行，折叠行 26，紧凑问题卡，问题行 36，隐藏正常摘要行 |

### 2.14 折叠行行为

4. “占用 App”展开后显示分段控件“CPU | 内存”与 5 行列表。默认按 CPU 排序。
5. “更多”展开后，从上到下显示以下内容：
   1. 磁盘 30 天曲线与 1/5/30 天增长（磁盘不是问题项时）。
   2. 网速 2 小时曲线（问题模式时）。
   3. 今天与近 5 天流量。
   4. 电池电量、电源与上次睡眠掉电（耗电不是问题项时）。
   5. CPU 传感器均值与风扇转速，标注“参考，不参与判定”。
6. 展开折叠行不改变面板高度。展开内容占用中部区域，超出部分在中部区域内部滚动，并自动滚到被展开的折叠行顶部（见 [2.11](#211-高度策略)）。

## 3. 菜单栏图标规格

### 3.1 构成

菜单栏图标的主体是比熊正面头像剪影：圆头、垂耳、三点脸挖空。图标是模板图（`isTemplate = true`），由系统按菜单栏外观着色。侧身站姿剪影不作为菜单栏默认，只在评审门未通过时作为备选（见 [9.4](#94-内部评审门)）。删除上一版的方块与水滴。

| 项 | 值 |
|---|---|
| 图像尺寸 | 24 × 18 pt，宽度固定。有无角标都是 24 pt，菜单栏其他图标不移位 |
| 头像区域 | x 0 至 19 pt，y 0.5 至 17.5 pt（AppKit 坐标，y 向上）。头部圆直径 14 pt，两耳垂在头侧 |
| 角标区域 | 右下角 10 × 10 pt，x 14 至 24，y 0 至 10 |
| 角标隔离 | 角标周围 1 pt 透明间隙（12 × 12 pt 的圆角方形），从头像剪影中挖空 |
| 渲染 | `NSImage(size:flipped:drawingHandler:)` 矢量绘制，1x 与 2x 自动适配 |

### 3.2 姿态集

姿态用头像表达整机最严重的等级。角标表达问题的类别。姿态之间的外轮廓必须不同。

| 整机最严重等级 | 姿态 | 头像特征 | 角标 |
|---|---|---|---|
| 绿 | 正常 | 耳朵放松，垂在头侧 | 无 |
| 黄 | 关注 | 耳朵翘起，耳尖向外上方张开约 20° | 最严重问题项的类别字形 |
| 红 | 警告 | 嘴张开，舌头伸出下颌 2.5 pt，耳朵竖起，比关注更高（I2 修订：与关注的 1x 异或比例因此从 0.08 升到 0.32） | 最严重问题项的类别字形 |
| 统计中、过期 | 空心 | 正常姿态的头像只画 1 pt 描边，不填充 | 无 |

### 3.3 角标

角标是 5 个可辨识的小字形，分别对应 5 个健康项。角标放大到 10 × 10 pt，一律实心，不使用挖空线。每个字形最多有 2 个特征。字形外形差别大，不依赖颜色。

| 健康项 | 字形 | 绘制规则（10 × 10 pt 框内） |
|---|---|---|
| CPU | 方块加一圈缺口 | 特征 1：中心 4.5 × 4.5 pt 实心方块。特征 2：外圈 9 × 9 pt 圆角环，线宽 1 pt，顶部留 3 pt 缺口 |
| 内存 | 长条 | 特征 1：横向 9 × 4 pt 实心圆角矩形。不加引脚：引脚会落进磁盘轮廓，1x 下与磁盘的比例只有 0.28 |
| 温度 | 胶囊加球 | 特征 1：竖向 3 × 6.5 pt 实心胶囊。特征 2：底部直径 5 pt 实心圆球 |
| 磁盘 | 圆柱 | 特征 1：宽 7 pt、高 9 pt 的实心圆柱外形，顶部与底部为圆弧 |
| 耗电 | 闪电 | 特征 1：6 顶点实心多边形，坐标 (5.5, 10)、(1.5, 4.5)、(4.5, 4.5)、(3.5, 0)、(8.5, 6)、(5.5, 6)，单位 pt，y 向上 |

耗电的最简版是闪电。电池轮廓不是实心字形，并且与内存的长条相近，所以不作默认。

字母方案（对照，也是评审门未通过时的备选）：

| 健康项 | CPU | 内存 | 温度 | 磁盘 | 耗电 |
|---|---|---|---|---|---|
| 字母 | C | M | T | D | P |

字母使用 SF Pro Rounded Bold，大写字高 8 pt，居中于 10 × 10 pt 框。

**已定选择：默认使用字形。** 选择依据是两条标准：

1. 1x 下可分辨度：5 个字形的轮廓面积差别大（长条、胶囊加球、闪电、圆柱、方环）。字母中 C、D、P 在 1x 下只有 8 像素字高，轮廓相近。
2. 一致性：状态卡内的类别字形与菜单栏角标使用同一套字形（见 [2.9](#29-图标与间距规则)）。字母方案会使两处不一致。

评审门判据（见 [9.4](#94-内部评审门)）：在 1x（10 × 10 像素）下，把每个角标渲染为位图，计算任意两个角标的不重合像素比例。比例 = 异或像素数 ÷ 两者中较大的实心像素数。5 个字形两两比例都必须 ≥ 0.35。任一对 < 0.35 时，字形方案不通过，改用字母方案，并用同一判据检查字母方案。

等级不由角标表达。角标只表达类别，不分黄红。黄与红由头像姿态表达（关注与警告）。

- 多个问题项时，角标显示排序第一的问题项（[2.4](#24-问题排序规则)）。完整列表在提示文字与无障碍文字中。
- 角标保持模板图，所有状态都不着色（见 [11](#11-已定决定) 的 K1）。

### 3.4 18 pt 简化规则

菜单栏版比熊由头像简化而来。简化规则如下：

1. 只画剪影，单色。头、两耳合并为一个并集路径。
2. 三点脸只用挖空表达：两只眼睛各为 1.9 pt 圆形挖空，鼻子为 2.3 × 1.8 pt 椭圆挖空（I2 修订：1.6 pt 在 1x 下不能清空一个整像素，CI 判据为像素 alpha < 0.02）。
3. 耳朵与头部之间用 0.75 pt 挖空线分开，让耳朵可读。
4. 毛发蓬松轮廓：头顶与头侧共 8 个圆凸，每耳下沿 2 个圆凸。每个圆凸半径 ≥ 1.25 pt（2x 下 2.5 px）。
5. 垂直与水平边对齐 0.5 pt 栅格，避免 2x 下发虚。
6. 最小线宽与最小挖空宽度都是 0.75 pt。
7. 3 个姿态必须改变剪影外轮廓，不能只改内部细节：耳朵放松与翘起的耳尖位置不同，伸舌增加下颌外的凸起。
8. 头像路径是手写的固定 Bezier 数据（见 [4.2](#42-外形来源手写路径与起始参考)），不由配方生成。

### 3.5 状态切换动画

菜单栏图标常态静止。只有整机最严重等级变化或角标类别变化时，播放 1 次切换动画。

| 项 | 值 |
|---|---|
| 帧数 | ≤ 8 帧 |
| 时长 | ≤ 600 ms（8 帧 × 75 ms） |
| 驱动 | 1 个一次性定时器，播放完立即作废 |
| 帧来源 | 由 `DogRig` 在两个姿态之间做部件变换插值生成（耳角、舌长），首次使用时生成并缓存 |
| 内容 | 正常到关注：耳朵翘起，角标从 0 放大到 1.2 再回到 1。关注到警告：张嘴、伸舌。降级：反向播放 |
| 节流 | 同一个健康项 5 分钟内最多播放 1 次。屏幕锁定或显示器睡眠时不播放，直接切换 |
| Reduce Motion | 不播放，直接切换到目标帧 |

### 3.6 无障碍文字与提示文字

`button.toolTip` 与无障碍标签使用同一段文字。文字按问题排序列出问题项，正常项放在最后，正常项按固定优先级。台式机没有电池，不列耗电。

| 场景 | 文字示例 |
|---|---|
| 全部正常 | “MoleMonitor：一切正常。温度、内存、磁盘、耗电、CPU 正常。” |
| 单项问题 | “MoleMonitor：磁盘异常，5 天多占用 314 GB，已持续 3 小时 12 分。温度、内存、耗电、CPU 正常。” |
| 耗电问题 | “MoleMonitor：耗电需留意，睡眠掉电 3.3%/小时，已持续 2 小时 10 分。温度、内存、磁盘、CPU 正常。” |
| 多项问题 | “MoleMonitor：4 项需要处理。磁盘异常，已持续 3 小时 12 分。内存异常，已持续 25 分。耗电需留意，已持续 40 分。CPU 需留意，已持续 40 分。温度正常。” |
| 统计中 | “MoleMonitor：正在统计。” |
| 过期 | “MoleMonitor：数据已过期，最后数据 13:40。” |

## 4. 比熊规格

### 4.1 造型方向

比熊犬有 6 个辨识特征：

1. 圆球形的头。
2. 深色的“三点脸”：两只眼睛加一个鼻子。
3. 垂在头侧、被毛发盖住的耳朵。
4. 羽毛状、卷在背上的尾巴。
5. 短腿。
6. 云朵一样的白色卷毛。

造型按“婴儿图式”放大头部：头部直径约等于身体高度。

### 4.2 外形来源：手写路径与起始参考

“椭圆加圆凸”的数学配方不能保证“像比熊”。因此配方只是**起始参考**。关键姿态的外形由工程师手写固定的 Bezier 路径数据决定。这个流程降低“画不像”的风险。

**降险流程：**

1. 工程师参照本节的起始参考配方，手写关键姿态的外轮廓与部件路径。关键姿态有 4 个：趴、站、小跑一帧、喘气。
2. 路径数据放进独立文件 `Sources/Core/DogArt.swift`。文件只含数字与枚举，不含绘制逻辑。该文件是美术资产，可以多次迭代，不需要改动 `DogRig`。
3. `DogRig` 只对部件做变换：腿相位、耳角、尾角、呼吸缩放、头部倾斜。`DogRig` 不生成外形。
4. 步态与姿态使用的基础路径如下：

| 基础路径 | 用于 |
|---|---|
| 趴 | 趴 |
| 站 | 站、走、统计中、过期 |
| 小跑一帧 | 小跑、冲刺 |
| 喘气（头部张嘴变体） | 温度红时替换头部与舌头 |

5. 第一交付物是静态图册（见 [4.8](#48-图册)），不是动画。图册包含状态卡版 104 × 78 pt 与 72 × 54 pt、菜单栏版 24 × 18 pt，各有 1x 与 2x，浅色与深色底。
6. 验收：图册通过内部评审门 G1（见 [9.4](#94-内部评审门)）后，才进入动画阶段。G1 未通过时，工程师修改路径数据，再次提交图册。

`DogArt` 的数据结构见 [8.1](#81-core-新类型纯-foundation)。设计坐标系为 120 × 90 单位（u），原点在左上，y 向下，比熊面朝右。地面线 y = 82。绘制时整体缩放到目标尺寸。

**起始参考：部件表（站姿）。** 工程师用下表起草路径，不直接用它渲染。

| 部件 | 基本图形 | 参数 | 颜色（浅 / 深） |

| 远侧后腿 | 胶囊加圆形爪 | 髋关节 (34, 60)，宽 9，关节到爪心 16，爪半径 5 | `fur.shade` |
| 远侧前腿 | 同上 | 肩关节 (64, 60) | `fur.shade` |
| 尾巴 | 4 个圆沿二次贝塞尔排列 | 曲线起点 (24, 40)，控制点 (10, 36)，终点 (16, 22)。圆在 t = 0.15、0.40、0.65、0.90 处，半径 6、7、7.5、6.5 | `fur` |
| 身体 | 椭圆加圆凸 | 中心 (52, 50)，rx 30，ry 18。上半圆周 9 个圆凸：角度 180° 至 360° 每 22.5° 一个，半径 8，圆心在椭圆边上。下沿 5 个圆凸：角度 30° 至 150° 每 30° 一个，半径 6 | `fur` |

**绘制顺序与描边：**

1. 先画地面阴影。
2. 描边层：把外轮廓路径与 `fur` 部件路径各自外扩 1.25 u，用 `fur.outline` 填充。手写路径本身带扇贝形的毛发边。
3. 毛发层：按部件表顺序用各自颜色填充。
4. 体积感：身体下半部叠加一个径向渐变，黑 6% 到 0%，半径 24 u。这是唯一的渐变，面积小于比熊面积的 20%。
5. 最后画脸部（眼、鼻、腮红、嘴）。

**性能要求：** 每个部件的 `Path` 在首次使用时由 `DogArt` 数据构建 1 次并缓存。每帧只对部件施加仿射变换（平移、旋转、缩放）后填充。不在每帧重新生成外形。

### 4.3 骨架参数

每一帧的姿态由下表参数决定。`DogRig`（Core，纯 Foundation）计算参数。`DogView`（App）只负责绘制。`DogRig` 只输出部件变换参数，不生成外形。外形来自 `DogArt` 的手写路径（见 [4.2](#42-外形来源手写路径与起始参考)）。

| 参数 | 含义 | 单位 |
|---|---|---|
| `bodyY` | 身体与头部的整体竖直偏移 | u |
| `bodyPitch` | 身体绕中心的俯仰角，正值为前倾 | 度 |
| `breath` | 身体纵向缩放增量 | 比例 |
| `headY`、`headTilt` | 头部偏移与倾斜 | u、度 |
| `earAngle` | 耳朵绕耳根的角度，负值为翘起 | 度 |
| `tailAngle` | 尾巴绕尾根的角度 | 度 |
| `legAngle[4]` | 4 条腿绕关节的摆角，顺序为远后、远前、近后、近前 | 度 |
| `legLift[4]` | 腿在前摆阶段的缩短比例，模拟屈膝 | 比例 |
| `mouthOpen`、`tongue` | 张嘴程度与舌头长度 | 0–1、u |
| `eyesClosed` | 闭眼程度 | 0–1 |
| `bundle` | 驮包的显示与鼓起程度 | 0–1 |
| `bubble` | 关注气泡的显示比例 | 0–1 |
| `speedLines` | 速度线透明度 | 0–1 |

### 4.4 姿态集

步态由 CPU 决定。叠加姿态由其他问题项决定。两者可以同时存在。

**步态（CPU）：**

| 步态 | 含义 | 动作要点 |
|---|---|---|
| 趴 | CPU 低，机器很闲 | `bodyY` +12。前腿向前平放（摆角 −75°），后腿收在身下（远侧后腿不画）。头部下移 12 u。眼睛半闭（`eyesClosed` 0.6）。呼吸：`breath` = 0.025 × sin(2π t / 2.0)，2 秒一次。尾巴平放（−50°），0.5 Hz 摆动 3° |
| 站 | 统计中、过期，菜单栏常态 | 中性姿态。状态卡内尾巴 1.2 Hz 摆动 6°，呼吸幅度 0.012，周期 2.5 秒 |
| 走 | 轻度负载 | 步频 0.8–1.4 Hz。摆幅 16°。四腿相位：远后 0、远前 0.25、近后 0.5、近前 0.75（单位为周期）。身体起伏 0.8 u × \|sin 2φ\|。头部起伏 0.5 u，滞后 0.1 周期。尾巴随步频摆动 8° |
| 小跑 | 中度负载 | 步频 1.6–2.4 Hz。摆幅 26°。对角腿同相：近前与远后相位 0，远前与近后相位 0.5。前摆阶段 `legLift` 0.15，爪抬高 3 u。身体起伏 1.6 u，频率为步频 2 倍。耳朵 ±8° 拍动，滞后 0.15 周期。尾巴上抬 10° |
| 冲刺 | 重度负载 | 步频 2.8–3.6 Hz。摆幅 40°。前腿对相位 0 与 0.08，后腿对相位 0.5 与 0.58（跑步）。身体俯仰 5° × sin φ。起伏 2.5 u。耳朵向后吹 −30°，加 5° 拍动。尾巴向后 −20°。身后 3 条速度线：长 10、14、8 u，粗 1.6 u，`text.secondary` 35%，位于 y 40、50、58，每个步频周期从 x 18 滑到 x 4 并淡出。地面阴影横向缩放 0.9–1.05 |

**叠加姿态：**

| 叠加姿态 | 触发 | 动作要点 |
|---|---|---|
| 喘气 | 温度为红（热状态 serious 或 critical） | 张嘴（`mouthOpen` 1），舌头长度在 7 与 9 u 之间以 2.5 Hz 变化。呼吸幅度 0.03，频率 2.5 Hz。头顶 2 条热气波浪线，线宽 1.2 u，透明度 30%，1.2 秒上升 6 u 并淡出，循环 |
| 驮包 | 内存为红（压力严重，或内存等级为红） | 背上一个包袱：圆角矩形，中心 (50, 26)，26 × 18 u，圆角 7，颜色 `#D9C3A0`（深色 `#BFA984`）。顶部打结：两个椭圆，中心 (44, 18)，rx 4，ry 3，分别旋转 ±30°。一条 2 u 宽的带子从 (38, 40) 斜到 (60, 62)，颜色 `#B79D74`。包袱以 1.6 秒周期鼓起 4%。负重：`bodyY` +2，步频与摆幅都乘 0.85 |
| 关注 | 任意问题项（黄或红） | 耳朵翘起（`earAngle` −25°），头部倾斜 8°。头部右上方一个思考气泡：主圆中心 (104, 4)，半径 9，两个尾圆半径 2 与 1.2 指向头部。气泡内画最严重问题项的字形（与菜单栏角标相同），10 u 高，颜色为对应等级的文字令牌。气泡出现时弹出 1 次（缩放 0.6 到 1），之后静止 |
| 灰化 | 统计中、过期 | 站姿静止，透明度 45%，无气泡，无动画 |

组合优先级：灰化覆盖一切。其余情况下，步态取 CPU，再叠加喘气、驮包与关注。

### 4.5 速度映射公式

**输入：** 整机 CPU 百分比（0 至 100）。状态卡打开时使用 2 秒细采样，打开前的第一个值取趋势缓冲的最新 30 秒点。没有任何值时，步态为站。

**第 1 步：指数平滑。**

```
α = 1 − exp(−Δt / τ)，τ = 8 秒
s ← s + α × (x − s)
```

打开状态卡时，s 的初值等于最新 30 秒点，比熊一出现就是正确的步态，不从 0 加速。

**第 2 步：带迟滞的步态选择。**

| 步态 | 向上进入：s ≥ | 向下离开：s < |
|---|---|---|
| 走 | 10 | 7 |
| 小跑 | 40 | 34 |
| 冲刺 | 80 | 72 |

- 低于“走”的离开值时为趴。
- 步态切换后至少保持 4 秒，才允许下一次切换。
- 任意 10 秒内最多切换 2 次。

**第 3 步：步态内的连续步频。**

```
f = f_lo + (f_hi − f_lo) × clamp((s − 进入值) / (上一档进入值 − 进入值), 0, 1)
```

冲刺档的范围取 80 至 100。

**第 4 步：步频限速与相位连续。**

- 步频变化率 ≤ 0.6 Hz/秒。
- 相位按 φ ← φ + 2π × f × Δt 累加，永不重置。因此步频变化不会造成腿部跳帧。

**第 5 步：步态过渡。**

- 走、小跑、冲刺之间切换时，所有骨架参数在 0.35 秒内用 smoothstep 插值。腿的相位偏移在圆周上插值。
- 趴与走之间切换时，播放 0.6 秒的起身或趴下过渡。

### 4.6 帧时序与成本预算

| 项 | 预算 |
|---|---|
| 驱动 | `TimelineView(.animation(minimumInterval: 1.0 / 24, paused: reduceMotion || isStatic))`，只在 `DogView` 内 |
| 帧率 | ≤ 24 fps |
| 单帧主线程绘制 | ≤ 0.4 ms（M1 基准） |
| 状态卡打开时 CPU 增量 | < 1% 单核 |
| 状态卡关闭时 | 视图已释放，0 帧，0 定时器 |
| 内存 | 部件路径缓存 < 50 KB |

如果真机测得单帧超过 0.4 ms，按备选方案处理：预渲染每个步态 12 帧的位图条，以 12 fps 播放（见 [10.3](#103-风险与备选)）。

### 4.7 Reduce Motion 降级

开启“减少动态效果”时：

1. `TimelineView` 暂停，比熊显示静态姿态。
2. 静态姿态取当前步态在 φ = π/2 处的帧（迈步中），让用户仍能看出步态。
3. 喘气显示伸舌静态帧，驮包显示不鼓起的包袱，关注气泡直接出现，不弹出。
4. 速度线与热气波浪线不画。

## 6. 数据层规格

数据层沿用 PROJECT.md 第 3 节与第 6 节。本节只写表现层需要的补充与变更。

### 6.1 采样计划与唤醒预算

本设计用 1 个 30 秒定时器替换现有的 5 分钟定时器。PROJECT.md 6.1 已经规定全机 CPU 每 30 秒采样，所以 30 秒是既定的最低唤醒频率。其他周期都是 30 秒的整数倍，在同一次唤醒中完成，不新增唤醒。

**状态卡关闭时（定时器周期 30 秒，容差 6 秒）：**

| 每第 N 次唤醒 | 周期 | 工作 |
|---|---|---|
| 1 | 30 秒 | 全机 CPU tick、网卡计数器、内存压力、swap、热状态。写入趋势缓冲 1 个点。评估 CPU、内存、温度健康等级 |
| 2 | 60 秒 | 电池供电时读电量与电源状态，写入趋势缓冲，评估整机耗电异常 |
| 6 | 180 秒 | 任一健康项为黄或红时进程扫描（单应用占满、占用 App 预读） |
| 10 | 300 秒 | 接电源时读电量与电源状态。全绿时进程扫描。写 `status.json` 与 `trend.json` |
| 30 | 15 分钟 | 磁盘采样（沿用现有逻辑） |

进程扫描的周期规则：

| 条件 | 进程扫描周期 |
|---|---|
| 状态卡关闭，全部健康项为绿 | 300 秒 |
| 状态卡关闭，任一健康项为黄或红 | 180 秒 |
| 状态卡打开 | 4 秒 |

电池的采样节奏沿用 PROJECT.md 6.1：电池供电 60 秒，接电源 5 分钟。睡眠前和醒来后各读一次电量，用于睡眠掉电（见 [6.8](#68-健康等级与已持续)）。

**状态卡打开时（另加 1 个 2 秒定时器，关闭时取消）：**

| 每第 N 次触发 | 周期 | 工作 |
|---|---|---|
| 1 | 2 秒 | 全机 CPU、网卡计数器、内存压力、swap、热状态。写入细段 |
| 2 | 4 秒 | 进程扫描，刷新占用 App |
| 3 | 6 秒 | SMC CPU 温度与风扇（只在“更多”展开或温度为问题项时） |

与 PROJECT.md 的差异：

| 项 | PROJECT.md | 本设计 | 理由 |
|---|---|---|---|
| 打开时进程扫描 | 5 秒 | 4 秒 | 对齐到同一个 2 秒定时器，不新增第二个定时器 |
| 打开时 SMC | 5 秒 | 6 秒 | 同上 |
| 关闭且全绿时进程扫描 | 180 秒 | 300 秒 | 全绿时占用 App 只用于折叠行预览，不需要更新得更勤 |

**事件源（不轮询）：**

| 事件 | 接口 | 处理 |
|---|---|---|
| 内存压力变化 | `DispatchSource.makeMemoryPressureSource(eventMask: [.normal, .warning, .critical])` | 立即更新压力值并评估 |
| 热状态变化 | `ProcessInfo.thermalStateDidChangeNotification` | 立即更新热状态并评估 |
| 睡眠与唤醒 | `NSWorkspace.willSleepNotification`、`didWakeNotification` | 沿用现有逻辑，睡前读电量并写 `trend.json`，醒后读电量并生成睡眠记录 |
| 电源切换 | `IOPSNotificationCreateRunLoopSource` | 立即更新电源状态。接电源时清空整机耗电窗口 |

**成本估算（待真机验证）：**

| 项 | 估算 |
|---|---|
| 30 秒一次的轻采样（含每 60 秒的电池读取） | < 0.5 ms |
| 进程扫描（约 600 个进程） | p95 ≤ 20 ms（V9） |
| 进程扫描次数 | 全绿 12 次/小时，黄或红 20 次/小时 |
| 状态卡关闭时 CPU 均值 | < 0.02% |
| 空闲唤醒 | 每分钟 2 次 |

### 6.3 趋势缓冲

趋势缓冲常驻内存，App 运行期间一直存在。它解决“每次打开曲线重新积累”的问题（U13）。

| 项 | 值 |
|---|---|
| 粗段 | 每 30 秒 1 个点，容量 240 个点（2 小时） |
| 细段 | 状态卡打开期间每 2 秒 1 个点，容量 150 个点（5 分钟）。关闭时清空 |
| 每点字段 | 时间、CPU、下行速率、上行速率、swap 已用、电量、内存压力、热状态、电源 |
| 每点内存 | 实测 stride 为 88 字节：`Date` 8 字节，5 个可选数值各占 9 字节并对齐到 8 字节边界，3 个 1 字节的可选枚举紧贴最后一个数值之后，总大小 84 字节，stride 为 88 字节。规划值取 96 字节/点，留出余量 |
| 总内存 | 规划值：(240 + 150) × 96 = 37,440 字节 ≈ 36.6 KB。实测值：390 × 88 = 34,320 字节 ≈ 33.5 KB。两者都小于 50 KB 上限，所以保留点数与编码方案不变 |
| 线程 | 引擎队列独占。向主线程发布不可变的 `TrendSeries` 快照 |

曲线绘制时的合并规则：

1. 横轴范围为 [现在 − 2 小时, 现在]。
2. 细段覆盖的时间范围内，去掉粗段的点，改用细段的点。两者不重复画线。
3. 状态卡刚打开时细段为空，曲线完全由粗段组成。因此打开第一帧就有 2 小时曲线。
4. 粗段与细段由两个 Chart 分别绘制（见 [2.7](#27-图表规则)）。

stride 的实测方法：用 Swift 6.4 在 Linux 64 位上对含电量与电源字段的 `TrendPoint` 调用 `MemoryLayout<TrendPoint>.stride`，结果为 88。不含电量与电源的旧布局为 72。macOS arm64 的结构体布局规则相同。Core 测试在 Mac 上复核（见 [9.1](#91-core-测试linux-与-macscriptstest_corepy)）。

### 6.4 落盘与恢复

| 项 | 值 |
|---|---|
| 文件 | 数据目录下的 `trend.json` |
| 写入时机 | 每 5 分钟（与 `status.json` 同一次唤醒）、睡前、退出时 |
| 写入方式 | 写临时文件，`rename` 原子替换。权限 0600 |
| 内容 | 只有粗段。细段不落盘 |
| 大小 | 约 9 KB |
| 每日写入量 | 约 2.6 MB |

文件格式（列式 JSON，数值取整以减小体积）：

```json
{"v":1,"t0":"2026-10-11T12:00:00Z","dt":[0,30,61,90],"cpu":[12.3,8.1,null,9.0],"rx":[1200,880,null,15],"tx":[80,40,null,3],"swap":[1288,1288,null,1290],"bat":[82,81,null,80],"mp":["n","n",null,"w"],"th":["n","n",null,"f"],"ps":["b","b",null,"b"]}
```

| 字段 | 含义 |
|---|---|
| `v` | 格式版本，当前为 1 |
| `t0` | 第一个点的时间（UTC） |
| `dt` | 每个点相对 `t0` 的秒数，整数 |
| `cpu` | CPU 百分比，1 位小数 |
| `rx`、`tx` | 下行与上行，KB/s，整数 |
| `swap` | swap 已用，MiB，整数 |
| `bat` | 电量百分比，整数。没有电池的 Mac 全部为 `null` |
| `ps` | 电源：`b` 电池供电、`a` 接电源 |
| `mp` | 内存压力：`n` 正常、`w` 警告、`c` 严重 |
| `th` | 热状态：`n`、`f`、`s`、`c` |
| `null` | 该点该字段缺失，不是 0 |

旧文件缺少 `bat` 或 `ps` 时，按全部为 `null` 读取，不丢弃文件。

恢复规则：

1. 启动时读取 `trend.json`。
2. 版本不是 1、JSON 损坏或数组长度不一致时，丢弃整个文件，从空缓冲开始。不报错，不弹窗。
3. 丢弃比“现在 − 2 小时”更早的点，丢弃时间晚于“现在”的点。
4. 恢复的最后一个点与启动后第一个点之间按 [6.5](#65-睡眠空洞与断点) 规则断开。

### 6.5 睡眠空洞与断点

1. 相邻两个点的间隔大于 3 倍采样周期（粗段 90 秒，细段 6 秒）时，两点之间是断点。
2. 断点处不连线。曲线分成多段，每段作为 Swift Charts 的一个 `series`。
3. 断点长度 ≥ 10 分钟时，在绘图区底部画一条 1 pt 点线横跨空洞，悬停提示“睡眠或未运行”。
4. 健康规则的窗口计算沿用 PROJECT.md 3.2：睡眠期间不计入窗口。

### 6.6 占用 App 前 5

**采集步骤（每次进程扫描）：**

1. 调用 `proc_listallpids` 取得全部 pid。
2. 对每个 pid 调用 `proc_pid_rusage(pid, RUSAGE_INFO_V6, …)`，读取 `ri_user_time`、`ri_system_time`、`ri_phys_footprint`、`ri_proc_start_abstime`。读取失败时，按 PROJECT.md 3.7 降级到 `proc_pidinfo(PROC_PIDTASKINFO)` 的 `pti_resident_size`，并标注口径为 RSS。两者都失败时，只计入“无权读取”数量。
3. CPU 时间单位：`ri_user_time` 与 `ri_system_time` 是 Mach 绝对时间单位，用 `mach_timebase_info` 换算为纳秒（验证项 V2）。
4. 用 `(pid, ri_proc_start_abstime)` 识别进程，避免 pid 复用。
5. 单个进程的 CPU% = Δ(用户时间 + 系统时间) ÷ Δ墙钟时间 × 100。单核满载为 100%。
6. 调用 `proc_name` 取得进程名（最长 32 字节）。
7. 调用 `proc_pidpath` 取得可执行文件路径，只在内存中用于找到最外层的 `.app` 包。路径不保存、不发布、不写入任何文件或提示词。
8. 读取 `.app` 包的 `CFBundleIdentifier` 与 `CFBundleDisplayName`（没有时用 `CFBundleName`）。按包路径缓存，最多 64 项。
9. 按 bundle id 合并为应用。没有 bundle 的进程用 `proc:<进程名>` 作为合并键。应用的 CPU% 是所属进程之和，可以超过 100%。应用内存是所属进程 footprint 之和。
10. 不读取 `KERN_PROCARGS2`，不读取任何进程参数或环境变量。

**系统进程判定：** 可执行文件路径以 `/System/`、`/usr/`、`/sbin/`、`/bin/`、`/Library/Apple/` 开头时，标记为系统进程。该判定在扫描时完成，只保留布尔值。

**忽略列表：** 沿用 PROJECT.md 3.2 的默认忽略列表（`mds_stores`、`mdworker`、`mdworker_shared`、`photoanalysisd`、`backupd`、XProtect 系列）。忽略列表中的进程不进入占用 App 前 5，也不参与单应用占满规则。MoleMonitor 自身不忽略。

**排序与显示：**

| 场景 | 排序 | 行数 |
|---|---|---|
| CPU 问题卡、温度问题卡 | CPU% 降序，相同时按内存降序 | 5（紧凑 3） |
| 内存问题卡 | 内存降序 | 5（紧凑 3） |
| “占用 App”折叠区 | 分段控件选择，默认 CPU | 5 |
| 提示词 | 跟随专项：内存专项按内存排序，其他按 CPU 排序 | 5（按长度规则可减到 3） |

- 只显示 CPU ≥ 0.5% 或内存 ≥ 50 MB 的应用。不足 5 个时，最后一行写“其余 App 占用很低”。
- 应用图标：`NSWorkspace.shared.urlForApplication(withBundleIdentifier:)` 取得包位置，再取图标并缩放到 16 pt。图标按 bundle id 缓存，最多 32 项，只在状态卡打开时加载，关闭时释放。
- 状态卡刚打开时，第一次扫描还没有差值。此时用“上一次后台扫描（全绿时最长 300 秒前，黄或红时最长 180 秒前）到本次扫描”的差值，列表标题写“占用 App（近 N 分钟）”。N 是距上次扫描的分钟数，向上取整，最大 5。4 秒后第二次扫描完成，标题改为“占用 App（实时）”。因此打开即有数据。

**泄漏检测：** PROJECT.md 3.7 的泄漏检测放在本次之后的批次实现（见 [10.1](#101-实现顺序)）。本次的内存等级只用内存压力与 swap 增长两条规则。

### 6.7 内存压力档位与 swap 趋势箭头

内存灯与内存问题卡显示 3 个量：压力档位、swap 已用、swap 趋势箭头。不显示百分比。

| 压力值 | 显示文字 |
|---|---|
| normal | 正常 |
| warning | 警告 |
| critical | 严重 |

swap 趋势箭头比较“现在”与“30 分钟前最近的点”的 swap 已用。

| 箭头 | 条件 | 无障碍读法 |
|---|---|---|
| `↑↑` | 30 分钟增长 ≥ max(2 GiB, 物理内存 12.5%)，即达到黄色进入阈值 | “swap 快速增加，30 分钟增加 X GB” |
| `↑` | 30 分钟增长 ≥ 512 MiB | “swap 增加，30 分钟增加 X GB” |
| `→` | 变化在 ±512 MiB 之内 | “swap 平稳” |
| `↓` | 30 分钟减少 ≥ 512 MiB | “swap 减少” |
| 不显示 | 30 分钟前没有点 | “swap 趋势统计中” |

### 6.8 健康等级与已持续

**阈值：** CPU、内存、温度、磁盘的进入条件、退出条件与迟滞全部沿用 PROJECT.md 3.2 至 3.5。本设计不修订阈值。理由：阈值已经是“持续时间加均值”的形式，满足用户要求 U7。阈值的复核仍按 PROJECT.md 的验证项（V1、V3）进行。耗电的睡眠掉电阈值沿用 PROJECT.md 3.6。整机耗电异常的阈值是本设计补充，见下文，复核用 V24。

**温度的显示文字：**

| 热状态 | 显示文字 |
|---|---|
| nominal | 正常 |
| fair | 偏热 |
| serious | 很热 |
| critical | 过热 |

**耗电（`power`）的规则：**

耗电是第 5 个健康项。它只来自电池电量读数。不显示每应用耗电，不用 CPU 估算耗电。

1. 没有电池的 Mac：`PowerHealth.evaluate` 返回 `nil`。耗电项不出现，不进入任何列表。
2. 睡眠掉电（沿用 PROJECT.md 3.6）：
   1. 条件：睡眠 ≥ 2 小时，且睡前使用电池。
   2. 掉电速率 = (睡前电量 − 醒后电量) ÷ 睡眠小时数。
   3. 黄：≥ 3%/小时。红：≥ 6%/小时。
   4. 接电源睡眠时，状态为 `not_applicable`。
   5. 问题开始时间取醒来时间。该问题保持到下一次 ≥ 2 小时的电池睡眠被判为绿，或醒来 24 小时后，以先到者为准。
3. 整机耗电异常（本设计补充，PROJECT.md 3.6 没有这条规则）：
   1. 条件：电池供电且未睡眠，连续 ≥ 60 分钟，期间没有接电源。
   2. 掉电速率 = 60 分钟窗口首尾电量之差 ÷ 窗口小时数。电量来自趋势缓冲的电池点。
   3. 黄：≥ 30%/小时。红：≥ 45%/小时。
   4. 退出：速率低于进入阈值的 80%，或接上电源。
   5. 窗口不足 60 分钟时，状态为 `insufficient_window`。
   6. 接上电源时清空窗口。
4. 合并：耗电项的等级取两条规则中更高者。等级相同时，取问题开始时间更早者。`reason_code` 为 `sleep_drain` 或 `awake_drain`。
5. 通知：睡眠掉电沿用 PROJECT.md 5.2（红色，冷却 6 小时）。整机耗电异常只在红色时通知，冷却 6 小时。
6. 采样节奏：电池供电 60 秒，接电源 5 分钟（PROJECT.md 6.1，见 [6.1](#61-采样计划与唤醒预算)）。

**等级的显示文字：** 沿用现有 `PanelFormat.levelText`：绿“正常”，黄“需留意”，红“异常”，灰“统计中”，过期“数据过期”。

**“已持续”的定义：**

1. 一次问题从健康项离开绿色开始，到回到绿色结束。
2. “问题开始时间”是进入条件第一次开始满足的样本时间，不是等级升高的时间。例如 CPU 黄的条件是“5 分钟均值 ≥ 70% 持续 5 分钟”。问题开始时间是 5 分钟均值第一次 ≥ 70% 的样本时间。
3. 黄升到红时，问题开始时间不变。红降到黄时，问题开始时间也不变。
4. 已持续 = 现在 − 问题开始时间。
5. 磁盘的问题开始时间沿用 `DiskEngineState.alertSince`。
6. 耗电的问题开始时间：睡眠掉电取醒来时间，整机耗电异常取掉电速率第一次达到进入阈值的样本时间。

**“已持续”的格式：**

| 时长 | 格式 |
|---|---|
| < 1 分钟 | 刚刚 |
| 1 至 59 分钟 | N 分 |
| 1 至 24 小时 | N 小时 M 分 |
| ≥ 24 小时 | N 天 M 小时 |

“已持续”只在问题项上显示。正常项不显示任何时长。

### 6.9 提醒与通知的问题优先

1. 提醒不单独成区。每条提醒并入对应健康项的问题卡或问题行。
2. 系统通知沿用 PROJECT.md 第 5 节的事件表、冷却时间与全局上限。整机耗电异常是设计补充事件：只在红色时通知，冷却 6 小时，去重键为 `power_awake_drain`。
3. 通知标题以健康项与等级开头，标题末尾带已持续。例如：“内存严重不足 · 已持续 32 分”“耗电异常 · 已持续 2 小时 10 分”。
4. 通知正文第一句写证据数字，第二句写下一步。例如：“swap 30 分钟增加 3.1 GB。点按查看，或复制给 Agent 排查。”
5. 通知带一个动作按钮“复制给 Agent”。点按该按钮时，App 把该专项的提示词写入剪贴板，不打开状态卡。点按通知本身时，App 打开状态卡，并展开该问题项。
6. 同一次评估产生多条通知时，先按 [2.4](#24-问题排序规则) 排序，按顺序消耗全局上限。然后按相反顺序投递，让最严重的通知显示在通知中心的最上方。
7. 不发恢复通知（PROJECT.md 5.1）。

## 7. 复制提示词规格

### 7.1 设计目标

提示词让用户的 agent 拿到 3 样东西：现在的状态与证据、需要排查的方向、可以安全使用的工具。提示词不臆造命令，不泄露隐私，长度 ≤ 3000 字符。

### 7.2 结构与选择规则

提示词由以下部分按顺序组成：

| 顺序 | 部分 | 来源 |
|---|---|---|
| 1 | 标题与请求 | 固定文字 |
| 2 | 环境 | 机型、芯片、内存、系统、App 版本、采样时间、新鲜度、CLI 路径 |
| 3 | 状态摘要 | 每个适用的健康项 1 行（4 或 5 行）：按问题排序列出，正常项在后 |
| 4 | 证据 | 占用 App 前 5 表、指标表 |
| 5 | 当前提醒 | 按问题排序，最多 3 条 |
| 6 | 我注意到的现象 | 占位符 `[在此描述你注意到的现象]` |
| 7 | 排查规则 | 固定文字，含安全规则与工具 |
| 8 | 专项 | 0 或 1 个专项段落 |

**提示词的范围（`PromptScope`）：**

| 范围 | 入口 | 状态摘要 | 证据 | 当前提醒 | 专项 |
|---|---|---|---|---|---|
| 总览 | 主按钮、`⌘C`、CLI 不带 `--topic` | 全部项 | 全部 | 全部（最多 3 条） | 自动选择 1 个 |
| 单个专项 | 问题卡与问题行的 `⧉`、通知动作、CLI `--topic` | 只有该项 1 行 | 只保留该专项需要的行 | 只有该项 | 指定的专项 |

**自动选择专项的规则：**

1. 有问题项时，选择排序第一的问题项对应的专项（[2.4](#24-问题排序规则)）。
2. 没有问题项时，不附加专项，并在“我注意到的现象”之后附加“例行检查”段（见 [7.3](#73-模板全文)）。
3. 网络没有健康等级，所以永远不会被自动选择。网络专项只能通过 CLI `--topic network` 或“更多”中网速区的 `⧉` 按钮获得。

健康项与专项的对应：磁盘 → `disk`，内存 → `memory`，CPU → `cpu`，温度 → `thermal`，耗电 → `power`。

### 7.3 模板全文

模板中 `{…}` 是占位符，[7.4](#74-字段映射) 给出映射。`{#if …}` 至 `{/if}` 是条件段。`{#each …}` 至 `{/each}` 是循环段。其他文字逐字输出。

**命令写法的已定选择：** 模板不使用 `mmcli` 别名。每条 CLI 命令直接写完整路径形式，例如 `{cli_path} --status`。“环境”一节也给出 `{cli_path}`。理由：`alias` 只在交互式 shell 中生效。agent 每次运行命令时通常使用新的非交互 shell，别名会失效。完整路径在任何 shell 中都有效。路径中的家目录前缀写 `~`，shell 会展开它。代价是提示词变长，所以长度上限定为 3000 字符（见 [7.6](#76-长度控制)）。

**总览模板：**

```text
# MoleMonitor 排查请求
请作为我的 Mac 维护助手，根据以下只读监测数据排查问题，并给出优化建议。

## 环境
- {model} · {chip} · 内存 {ram} · macOS {os}
- MoleMonitor {app_version} · 采样于 {sampled_at} · {freshness}
- CLI：`{cli_path}`

## 状态摘要
| 项 | 等级 | 当前 | 已持续 |
|---|---|---|---|
{#each summary_rows}| {item} | {level} | {current} | {since} |
{/each}
## 证据
{#if apps}| App（{apps_basis}） | CPU | 内存 |
|---|---|---|
{#each apps}| {app_name} | {app_cpu} | {app_mem} |
{/each}
{/if}| 指标 | 值 |
|---|---|
{#each evidence_rows}| {label} | {value} |
{/each}
## 当前提醒
{#if alerts}{#each alerts}{n}. [{level}] {message}
{/each}{/if}{#if no_alerts}无。
{/if}
## 我注意到的现象
[在此描述你注意到的现象]
{#if routine}
## 例行检查
当前没有提醒。请做一次快速体检：
1. 运行 `{cli_path} --disk-history --days 30`，看磁盘是否持续增长。
2. 运行 `mo status --json`，看是否有长期高占用的进程。
3. 只汇报发现，不做任何改动。
{/if}
## 排查规则
1. 先只读诊断，再给建议。
2. 删除、卸载或清理前，先列清单（对象、大小、理由），等我确认。
3. 不用 sudo，不改 SIP、登录项、风扇、SMC 或电源设置。
4. 只读工具：`{cli_path} --status`、`{cli_path} --disk-history --days 30`、`mo status --json`、`mo history --json`。数据目录：`{data_dir}`。
5. Mole 清理只用预览：`mo clean --dry-run`、`mo purge --dry-run`、`mo installer --dry-run`。
6. 命令报错时先运行 `<命令> --help`，不猜命令名或参数。
7. 回复：结论一句 → 证据 → 下一步（标明是否改动系统）。
{topic_section}
```

**磁盘专项（`disk`）：**

```text

## 专项：磁盘增长
口径：真实已用已排除可清除空间。增长量 = 当前值 − 窗口内最低值。
1. 运行 `{cli_path} --disk-history --days 30`，找出增长集中的日期。
2. 运行 `mo analyze --json ~` 找最大目录，再对其中最大的子目录运行 `mo analyze --json <目录>`。不要不带 --json 运行 `mo analyze`，交互模式可能把文件移到废纸篓。
3. 对照日期判断来源：下载、虚拟机镜像、Xcode 数据、容器镜像、照片库、本地备份。
4. 列出可回收项：路径（家目录写 ~）、大小、能否再生成。只用 dry-run 预览。
```

**内存专项（`memory`）：**

```text

## 专项：内存
口径：看内存压力与 swap 增长，不看已用百分比。
1. 运行 `sysctl vm.swapusage` 与 `vm_stat`，确认 swap 与压缩内存。
2. 运行 `ps -Ao pid,rss,comm -m | head -n 15`，对照上表找出大户。
3. 5 分钟后再运行第 2 步。持续上涨的 App 可能有泄漏。
4. 建议顺序：重启该 App → 减少标签页或扩展。不建议 `sudo purge` 或内存清理软件。
```

**CPU 专项（`cpu`）：**

```text

## 专项：CPU
口径：单核满载为 100%，多核可超过 100%。
1. 运行 `ps -Ao pid,pcpu,time,comm -r | head -n 15`，找出占用最高的进程。
2. 1 分钟后再运行一次，区分短时尖峰与持续占用。
3. 系统进程（mds_stores、mdworker、photoanalysisd、backupd）：说明用途，通常等它完成，不结束它。
4. 用户 App：先建议保存并正常退出，不直接 `kill -9`。
```

**温度专项（`thermal`）：**

```text

## 专项：温度
口径：等级来自系统热状态 thermalState，不是传感器读数。
1. 运行 `pmset -g therm`，确认是否有降频记录。
2. 对照上表的 CPU 占用找出热源进程。
3. 检查环境：是否放在软面上、是否接外接显示器、是否在充电。
4. 只建议降低负载，不建议控制风扇或修改 SMC。
```

**耗电专项（`power`）：**

```text

## 专项：耗电
口径：耗电来自电池电量读数，不来自 CPU 估算。睡眠掉电 = 睡眠前后电量差 ÷ 睡眠小时数。
1. 运行 `pmset -g batt`，确认电源、电量和充电状态。
2. 运行 `pmset -g assertions`，找出阻止睡眠的进程。
3. 运行 `pmset -g log | tail -n 200`，查看最近的睡眠与唤醒记录。输出很长，必须截取。
4. 上表的 CPU 与内存只是线索，不能换算成耗电。
5. 只建议退出阻止睡眠的 App。不运行不带 -g 的 pmset，它会修改电源设置。
```

**网络专项（`network`）：**

### 7.5 脱敏规则

| 编号 | 规则 |
|---|---|
| S1 | 进程只输出显示名与 bundle id。不输出 pid、可执行文件路径、命令参数、环境变量 |
| S2 | 所有路径中的家目录前缀（`NSHomeDirectory()`）替换为 `~` |
| S3 | 任何输出文字中出现的短用户名（`NSUserName()`）与全名（`NSFullUserName()`），整词替换为 `<用户>`。整词的定义见 S3.1，例外见 S3.2 与 S3.3 |
| S3.1 | 整词的定义：英文与数字的整词，其前后字符不是字母、数字或下划线，匹配时忽略大小写。中文的整词，其前后字符不是汉字、字母或数字 |
| S3.2 | 长度限制只针对短用户名：长度 < 3 个字符的短用户名不做整词替换，只做 S2。2 至 3 个汉字的中文全名不受此限制，按 S3.1 做整词替换 |
| S3.3 | App 名保护：App 显示名（去掉首尾空格，忽略大小写）整体等于短用户名、全名或其中任一片段时，保持原样，不替换。原因：替换会让 agent 认不出这个 App，而且整体相等不泄露额外信息。App 显示名只是包含这些文字时，仍按 S3.1 处理 |
| S4 | 不输出电脑名（`ComputerName`、`LocalHostName`），因为它常含真实姓名 |
| S5 | 不输出序列号、硬件 UUID、Wi-Fi 名称（SSID）、IP 地址、MAC 地址 |
| S6 | 不输出卷名以外的磁盘信息。卷挂载点只输出 `/System/Volumes/Data` |
| S7 | 提醒的 `message` 也经过 S2 与 S3 处理 |
| S8 | 最后一步：对整段提示词再执行 1 次 S2 与 S3，作为兜底。S8 同样遵守 S3.1 至 S3.3 |

### 7.6 长度控制

长度按 Swift `String.count`（字形簇）计算，上限 3000。**只有超过 3000 时才触发压缩。** 超出时按以下顺序逐步压缩，每步之后重新计算，达到上限即停止：

| 步骤 | 压缩内容 |
|---|---|
| L1 | App 名去掉 bundle id |
| L2 | 占用 App 减到 3 行 |
| L3 | 指标表去掉“磁盘增长”的 30 天值与“CPU 2 小时”行 |
| L4 | 当前提醒减到 2 条 |
| L5 | 状态摘要中正常项合并为 1 行：“其余 | 正常 | 温度、CPU | — ” |

- 安全规则（排查规则第 1 至 7 条）与专项段落永不压缩。
- 黄金测试覆盖最长场景：5 项全红（温度、内存、磁盘、耗电、CPU）、5 个 App 都是 32 字符名并带 45 字符的 bundle id、提醒 3 条、指标表 6 行、磁盘专项。该场景不压缩时为 2288 字符，小于 3000，所以不触发压缩。
- 如果任何场景压缩到 L5 后仍超过 3000，这是模板缺陷。测试失败，不在运行时截断。

压缩步骤的测试：用 `PromptOptions.maxLength` 覆盖上限，在同一个最长场景（5 项全红）上断言每步的结果。

| 测试上限 | 触发的最后一步 | 压缩后字符数 |
|---|---|---|
| 2200 | L1 | 2053 |
| 2000 | L2 | 1957 |
| 1930 | L3 | 1913 |
| 1900 | L4 | 1871 |

最长场景全部为红，没有正常项，所以 L5 不改变文字。L5 用示例场景（磁盘红加内存黄）测试：上限设为 1620，压缩到 L5 后为 1602 字符。该示例不压缩为 1823 字符，L1 后为 1738，L3 后为 1638。

| 入口 | 位置 | 复制的范围 | 反馈 |
|---|---|---|---|
| 主按钮 | 问题模式：问题区之后，文字“复制给 Agent · {最严重项}”。安静模式：底栏左侧文字按钮“复制状态给 Agent” | 总览 | 文字变为“✓ 已复制”，1.5 秒后恢复 |

交互细节：

1. 点击时，在主线程用当前发布的引擎快照生成提示词。生成耗时目标 < 2 ms。
2. 写入剪贴板：`NSPasteboard.general.clearContents()`，然后 `setString(text, forType: .string)`。只写纯文本一种类型。
3. 写入成功后，按钮文字变化。按钮宽度固定，文字变化不改变布局。
4. 1.5 秒的恢复用 `Task.sleep`，不创建 `Timer`。
5. 支持触控板的设备上，调用 `NSHapticFeedbackManager.defaultPerformer.perform(.generic, performanceTime: .now)`。
6. VoiceOver 播报“已复制排查提示词”（`NSAccessibility.post(element:notification:.announcementRequested, …)`）。
7. 复制后状态卡保持打开。用户切换到其他 App 时，状态卡按 `.transient` 行为自然关闭。
8. 主按钮的无障碍标签写“复制排查提示词给 Agent，围绕{最严重项}”。`⧉` 的标签写“复制{项}问题的排查提示词”。
9. “提示词包含 App 名称”默认开启。该设置保存在 `UserDefaults`，同时写入 `status.json` 的 `prompt_prefs`，让 CLI 使用相同设置。

**每个门的流程：**

1. CI 产出评审包（检查 M18）。
2. 主会话（协调者）查看 CI 截图与图册，按本门的清单逐项自评，并写下每项的结论。
3. 主会话请 Fable 导师做视觉评审。评审提示词引用用户的原话，不以转述代替。导师给出意见、指导，以及方向错误与预期错误的清单。
4. 每一项都通过，才进入下一阶段。主会话把导师意见中与用户原话冲突的部分记录下来，并以用户原话为准。
5. 有一项未通过时，工程师修改，重新提交评审包。每个门最多 3 轮。
6. 3 轮后仍未通过时，启用该门的备选方案，并把原因写进 [docs/VERIFICATION.md](VERIFICATION.md)。不降低通过标准。
7. 评审结论的摘要写进 [docs/VERIFICATION.md](VERIFICATION.md)。图像原件不提交。

## 11. 已定决定

以下决定由设计团队按获奖标准自行拍板。每条写明选择与理由。用户在全部工作完成后验收（见 [9.3](#93-最终验收清单真机用户逐项确认)）。开发过程中不向用户提问。

| 编号 | 决定 | 选择 | 理由 |
|---|---|---|---|
| K1 | 菜单栏角标是否着色 | 不着色，所有状态都用模板图 | 模板图在任何壁纸和菜单栏颜色下都清晰。角标只表达类别，等级由头像姿态表达 |
| K2 | 磁盘是否常驻灯列 | 不常驻。磁盘有问题时作为问题灯上浮 | 用户把磁盘定为次要信息。常驻会稀释“内存、CPU、温度”三灯 |
| K3 | 耗电是否常驻灯列 | 不常驻。耗电有问题时作为问题灯上浮 | 与磁盘同类。台式机没有电池，常驻灯会无意义 |
| K4 | 内存是否额外显示百分比 | 不显示。只显示压力档位、swap 已用与趋势箭头 | 系统的内存压力本身是档位。百分比会被误读为“已用内存” |
| K5 | 角标用字形还是字母 | 字形。字母（C、M、T、D、P）是评审门 G1 未通过时的备选 | 1x 下 5 个字形的轮廓差别大，字母 C、D、P 相近。字形还与状态卡内的类别字形一致。判据见 [3.3](#33-角标) |
| K6 | 菜单栏主体是头像还是侧身站姿 | 比熊正面头像剪影。侧身站姿是备选 | 头像在 18 pt 下更易辨认，三点脸挖空是比熊的特征 |
| K7 | 折叠行展开时面板是否长高 | 不长高。展开内容在中部区域内部滚动 | 用户要求高度只取 3 档。固定高度也避免展开时的闪动 |
| K8 | 整机耗电异常的阈值 | 电池供电 60 分钟窗口，黄 ≥ 30%/小时，红 ≥ 45%/小时 | PROJECT.md 3.6 只定义睡眠掉电。这两个值是设计补充。最终验收的 D15 与 V24 复核 |
| K9 | 提示词里的 CLI 写法 | 完整路径，不用别名 | `alias` 在非交互 shell 中失效。理由见 [7.3](#73-模板全文) |
| K10 | 提示词长度上限 | 3000 字符 | 完整路径使提示词变长。3000 字符不触发压缩，agent 拿到完整证据 |
| K11 | 主按钮高度 | 36 pt | 版面计划、`PanelMetrics` 与线框都按 36 pt 计算，且大字号下余量足够 |
| K12 | 比熊外形的来源 | 手写固定 Bezier 路径。数学配方只是起始参考 | 配方不能保证像比熊。手写路径可以逐轮迭代，不影响 `DogRig` |
| K13 | 用户何时参与 | 只在最后验收。中途用内部评审门代替用户确认 | 用户要求设计团队自行拍板。评审门由主会话自评加导师评审 |
| K14 | 灯列与摘要的顺序 | 全部使用 `ProblemOrder.all`：问题项在前，正常项按固定优先级（温度、内存、CPU） | 原则 P1 要求同一套排序规则用于所有位置 |
| K15 | 动画阶段何时开始 | 图册通过评审门 G1 之后 | 先确认“像比熊”，避免在不像的外形上做动画 |
